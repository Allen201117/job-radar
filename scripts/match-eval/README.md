# 岗位推荐方向准确性评测器

**用途**：改任何匹配链路（`lib/china-keyword-expansion.js` / `lib/opportunities/*` /
`lib/scoring.ts` / `lib/jobs-store/opportunities.ts` 的召回）之后，跑这套对拍确认
「推给用户的岗位，方向是不是对的」。

## 为什么单测不够

本轮（2026-09-01）查出的六个根因，**单测一个都没报警**——每条规则单独看都符合预期，
只有喂真实岗位库才看得出组合起来把方向带偏了：

| 根因 | 症状（真实库实测） |
|---|---|
| 技能词当方向词 | 数据分析师被推「结算专员」，卡片写「方向匹配：Excel」 |
| AI 领域词混在算法组 | 「阿里云运维工程师」被判成算法岗精确匹配 |
| 移动端混在前端组 | 前端工程师 TOP10 塞满 Android Framework / iOS |
| 研发巨桶内互串 | 算法↔运维↔后端↔测试 靠 JD 正文里的泛技术词互相命中 |
| 残差把职级后缀当硬条件 | 「前端开发工程师」的残差「开发」把真前端岗全挤出 exact |
| 召回池被泛词稀释 | 泛工程师岗 82,738 个 vs 真前端岗 1,225 个，1,800 预算全被前者吃掉 |

## 跑法

```bash
set -a; source .env.local; set +a          # 需要 JOBS_DATABASE_URL + SILICONFLOW_API_KEY

node scripts/match-eval/parse-resumes.js   # ① 6 份样例简历 → 真实 LLM 解析 → 画像
node scripts/match-eval/eval.js            # ② 真实召回 SQL + 真实匹配引擎 → 各画像的展示岗位
node scripts/match-eval/judge.js           # ③ LLM 独立裁判 → 方向准确率
```

三步都要跑；`eval.js` 依赖 ① 的产物，`judge.js` 依赖 ② 的产物。
本机需要 `psql`（脚本用它连香港 jobs 库；Node 侧 pg 直连要 `JOBS_DATABASE_SSL_CA`，本地通常没有）。

## 两个维度是刻意分开的

| 维度 | 输入 | 反映什么 |
|---|---|---|
| **A** 后端 / 结构化 | 只给干净的目标岗位 + 城市 | 匹配器本身的能力上限 |
| **B** 前端 / 简历画像 | 逐字等同用户传简历后落库的 `user_preferences` + `candidate_profiles`（含十几个技能词） | 用户真实体验到的准确率 |

**B 明显低于 A = 简历解析产出的画像在污染匹配**。2026-09-01 修复前差 5.3 个点
（A 78.7% / B 73.3%），修复后差 0.7 个点（A 98.0% / B 97.3%）。
这个差值本身就是一个要盯的指标——它一旦重新拉开，多半是简历解析那侧又往画像里塞了脏东西。

## 裁判为什么不用 `classifyJobFunction`

那是**被测对象**，拿它当裁判是循环论证（它本身 34.6% 的岗位判「其他」，英文标题几乎全漏）。
`judge.js` 用 LLM 独立判「岗位方向 vs 求职方向是否同一大方向」，与被测代码零耦合。

## 加新画像

往 `resumes/` 扔一个 `.txt`，重跑三步即可。样例覆盖了产品 / 算法 / 前端 / 数据 / 市场运营 /
财务六类，其中**前端和算法是最容易翻车的**（同属「研发」职能桶，细分方向靠词库区分）。

## 跨行业走查（2026-09-02 加，不烧 LLM）

`resumes/` 那 6 份是**互联网**画像。产品面向全行业，所以另备了一份**手写**的跨行业画像
（产品经理 / 机械工程师 / 临床护士 / 银行柜员 / 中学数学教师 / 土木工程师），
跳过简历解析这一步，直接喂给 eval：

```bash
set -a; source .env.local; set +a
PROFILES=scripts/match-eval/cross-industry-profiles.json node scripts/match-eval/eval.js
```

**它抓到的东西单测和互联网画像都抓不到**：2026-09-02 用它实测出银行柜员 / 中学数学教师 /
土木工程师三个画像的推荐数是 **0**（召回 1800 条，全被 role_mismatch 滤掉），
根因是 `CHINA_KEYWORD_GROUPS` 25 组全是互联网口径，非互联网方向词一个组都命中不到。

⚠️ **看展示数少不要急着改匹配，先查供给**。同日实测：深圳在招「柜员」岗全库只有 2 个，
广州「护士」8 个 —— 这两个画像展示 2 和 7，其实已经接近 100% 覆盖，是供给面问题不是匹配问题。
查法：
```sql
select count(*) from jobs where status='active' and title ~ '柜员|柜面' and location like '%深圳%';
```

## 两档准确率（2026-09-02 改，别再只看一个数）

旧版裁判只判「同一大方向」，判据里明写「不要求细分完全一致」→「产品运营」对「产品经理」
算同方向 → 报出 97.3%。但创始人在生产上看到的就是产品运营被推给产品经理用户
（实测那一版产品经理画像 339 条展示里 63 条是产品运营，18.6%）。**数字没造假，是尺子太松。**

现在 `judge.js` 判四档并分别报：
- **严格**（same_role）= 同一具体角色，用户会真去投 —— 这才是产品要盯的
- **宽松**（same_role + same_family）= 同大方向即可，等于旧口径
- unclear（标题没岗位信息）单独报，不计入分母

**两个数拉开 = 推荐"沾边但不对口"**，正是用户会抱怨的那种体感。
