# 设计组件库 — 决策记录

- 日期：2026-09-04
- 状态：✅ 已落地（第一批）
- 用法手册在 `DESIGN.md` 的「组件库」一节；本文只记**为什么这么选、否掉了什么**。

## 一、问题定义：不是「没规范」，是「规范没有尺寸轴」

立项时的假设是「全站样式散、缺一套规范」。读代码后这个假设被推翻了：
`app/globals.css` 里已经有一套完整的语义系统（`.t-*` 字阶、`.ink-*` 墨色、
`.btn-ink/.btn-ghost/.btn-soft`、`.surface/.chip/.eyebrow`），**连暗色都配齐了**。

真正的病根是这套 CSS 类**每个只有一个写死的尺寸**。想要小一号的按钮，就只能把整串样式
连暗色一起抄出来。证据链：

| 观察 | 数字 |
|---|---|
| 墨色按钮被手抄成几种尺寸 | **11 种**（CSS 只提供 2 种） |
| 白底次按钮被手抄成几种尺寸 | **10 种**（CSS 只提供 1 种） |
| `today-client.tsx:88` 手写的暗色 | 与 `.dark .btn-ink` 的定义**逐字节相同** |
| `cva`（专治变体轴，已装在项目里） | **0 次调用** |

所以方案的核心不是「再写一套规范」，而是**给已有规范补上尺寸轴 + 一个 React 封装层**。

## 二、关键决策与被否掉的选项

### 决策 1：颜色收成令牌，但**只收成对出现的**

创始人明确要求「严格 1:1，一个像素不准变」。这与「组件库要能改一处全站生效」表面冲突，
解法是：**令牌层如实记录现状的每一个值**（不归并），但每个值只有唯一定义点。
将来要不要归并变成改一行的事，而不是再翻 763 处。

可行性的关键证据：六族颜色**完美成对**——每个亮色值的 `dark:` 用量都是 0，每个暗色值几乎
全带 `dark:`。说明这 469 次手写本来就是「一族两态」，只是没人给它起名字。

- ❌ **否掉：全部收成令牌。** 只有亮色没有 `dark:` 的地方，换成令牌会让它在暗色下变色
  ——那是像素改动。这类一律跳过。
- ❌ **否掉：不管变体前缀直接替换。** 写转换器时发现 `hover:bg-[#dcf2e8]` 会被误当成
  基础态换掉，暗色下 hover 取值就跟原来不一样。正则加了 `(?<![:\w-])` 挡掉所有变体前缀。

### 决策 2：cva 只加尺寸轴，**颜色继续由 CSS 类提供**

`buttonVariants({variant:'ink', size:'sm'})` 返回 `btn-ink-sm px-4 py-2 …`，颜色一个字没写。
靠的是 Tailwind 的层序：`@layer components` 排在 `@layer utilities` 之前，padding 工具类
必然覆盖 CSS 类自带的值，而颜色/暗色/hover 全部原样继承。

- ❌ **否掉：把颜色抄进 cva 变体表。** 那会制造第二份颜色定义，正是要消灭的东西。
- ⚠️ 一处刻意的复杂：`ink` 用 `compoundVariants` 按尺寸切换底座类（lg → `.btn-ink` 带落影，
  其余 → `.btn-ink-sm` 无落影）。因为「大按钮浮起、卡内小按钮不抢视线」是原设计的刻意区分，
  一律套 `.btn-ink` 再想办法关掉落影会引入 `!important` 且破坏 1:1。

### 决策 3：变体表放 `.ts`，不放 `.tsx`

`tests/_load-ts.js` 只递归转译 `.ts`，加载不了 `.tsx`。变体表放 `lib/ui/variants.ts`，
契约测试就能**真的加载它做断言**（「ink 的小号必须不带落影」可被机器验证），
而不是只能 grep 字符串。

有意思的是：调研成熟库时得到了同一个结论的另一条路径——Radix Themes 把
`button.props.ts` 与 `button.tsx` 分开，理由是 props 声明与实现分离。两条路殊途同归。

### 决策 4：活文档用产品内的 `/design` 路由，不用 Storybook

`/design` 跑在真实产品里、用同一份 `globals.css` 和同一套 Tailwind 配置，
**不可能出现「文档站好看、线上不一样」**。

这一点有现成的教训：`DESIGN.md` 此前声称 `--primary: 210 100% 40%`（蓝），
实际是 `153 96% 36%`（绿）；它记录的 5 个 pastel 色值在 `globals.css` 里**根本不存在**。
纯文档必然漂移，活文档不会。

- ❌ **否掉：Storybook。** 要单独跑进程、单独配构建。GitHub Primer 用它是为了支撑 30+ 人
  和多主题多色盲模式对齐，这个规模不值。
- ❌ **否掉：Playwright 截图回归。** Primer 仓库里存了几百张 PNG，CI 一跑几分钟。
  设计还在打磨期，快照会天天失效。等设计稳定再说。
- ❌ **否掉：Style Dictionary 令牌流水线 / Ant Design 的 CSS-in-JS / 每组件一个目录。**
  理由见 `DESIGN.md`「门禁」一节的表格。

### 决策 5：门禁用契约测试，不引 lint 插件

调研建议加 `eslint-plugin-tailwindcss` 机械禁止硬编码色。否掉：它会对全站存量的近千处
硬编码一起报警，等于装了个永远红的灯。沿用本仓库「读源码做断言」的既有手法，
能**精确限定只管 `components/ui` 与 `lib/ui`**，且零新依赖。

这道门写完当场就抓出了作者自己的违规（Modal 遮罩里的 `#1a1714`），已收成 `--overlay-backdrop`。

### 决策 6：废弃走 `deprecated/` 子目录（学 Primer）

直接删组件会把「组件库改版」变成「全站必须同一天跟着改完」，几个人的团队做不到，
结果就是没人敢改组件库。搬走 + `@deprecated` JSDoc 之后，IDE 自动给调用处画删除线，
迁移可以按自己的节奏来。

第一个住户就是 `LEGACY_INPUT_CLASS`：它与组件库的 `<Input>` 在圆角、内距、聚焦光环、
暗色边框四处都不同，直接换会改像素；收进 deprecated 既消掉了三份重复，又把
「这里欠一次迁移」显式标了出来。

## 三、实测验证（不是推理）

在 dev server + 真实浏览器里量的计算样式：

| 令牌 | 亮色计算值 | 对应原硬编码 | 暗色计算值 | 对应原硬编码 |
|---|---|---|---|---|
| `tone-rose-fg` | `rgb(156,74,60)` | `#9c4a3c` ✓ | `rgb(230,169,159)` | `#e6a99f` ✓ |
| `tone-sky-bg` | `rgb(220,234,250)` | `#dceafa` ✓ | `rgba(127,178,232,0.15)` | `/[0.15]` ✓ |
| `tone-sky-border` | `rgb(183,210,238)` | `#b7d2ee` ✓ | `rgba(127,178,232,0.3)` | `/[0.30]` ✓ |
| `tone-green-fg` | — | — | `rgb(163,208,106)` | `#a3d06a` ✓ |
| `tone-amber-bg` | — | — | `rgba(224,177,90,0.15)` | `/[0.15]` ✓ |

Modal 六项行为实测全部通过：`role`/`aria-modal` 齐全、焦点进入弹层、Tab 到底循环回顶部、
打开锁滚动、ESC 关闭、关闭后焦点归还触发按钮。

> 有一次假阴性值得记：「焦点归还」第一次测出 `false`，原因是用 `.click()` 程序化点击
> **不会让按钮获得焦点**，`restoreTo` 捕获到的是 `body`。补 `focus()` 模拟真实鼠标点击后通过。
> 教训：测焦点行为时，程序化点击与真实点击的差异会伪造出 bug。

## 五、没做的事（下一轮候选）

- `<Button>` 尚未替换页面层的手写按钮（28 个文件）。已建好组件与 `buttonVariants()`，
  但逐个替换要保证 1:1，量大，留给「碰到再换」。
- 9 处手写 `animate-spin` 未换成 `<Spinner>`。
- 17 处空状态未换成 `<EmptyState>`。
- `JobFilters` 里那个成熟的 `Popover` 实现已被复刻进组件库，但原文件仍用自己那份
  （替换它要动 476 行的筛选器，风险 / 收益不划算）。
- **归并「差一点点」的同类颜色**（如 sky 的两种底色 `#dceafa` 与 `#e8f1fc`、
  lilac 的三种暗色强调 `#c3b1e6`/`#b9a3e0`/`#a98fd6`）。这是一次**有意的视觉决定**，
  需要创始人拍板，不能顺手改掉。
