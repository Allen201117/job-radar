# 职业洞察 v3：重定范畴 + 结构化数据模型（2026-09-03 立项）

> 创始人退回 v2 的原话口径：**「我们能爬的信息大多数不能给用户明确的承诺——不能说哪家公司一定轻松、一定高薪。这些按部门和业务区分，不同公司的业务和部门差异很大（字节的 Seed、腾讯的混元、阿里的千问）。能爬的信息有很多，要归好类放进数据集，以后索引、筛选、治理才好治理。」**
>
> 本文是这块的独立工程立项。工区 `claude/insights-v3-scope`。遵循 CLAUDE.md 新立的「工程化底线」。

---

## 0. 一句话结论

**v2 的错不在链路，在范畴与承诺**：它把「公司」当匀质对象，把「别人在网上说的」包装成「事实·公开来源」。

v3 做三件事：
1. **承诺分层**：把内容分成「我们能算的（第一方）/ 官方说的 / 别人说的」，措辞与视觉分明，**绝不把第三类说成事实**。
2. **主体下沉**：第一方统计的单位从「公司」下沉到「公司 × 业务线」，让「在招什么、扩张还是收缩」可下钻。
3. **结构化**：内容从散文改成「带主体、带口径、带时点、带样本量」的结构化断言，可索引、可筛选、可治理。

⚠️ **先读 §1.5**：用户最关心的四件事（强度/薪资/晋升/面试）里，岗位库只能答「稳定性」一件——
这个边界是本方案的前提，不认它就会再做一个 v2。

## 1. 为什么必须重做（实测证据）

### 1.1 v2 线上现状（2026-09-03 实测）

| 事实 | 数字 |
|---|---|
| active 洞察条目 | 6,253 条 / 516 家公司 |
| 有在招岗位的公司 | 1,988 家 → **74% 的公司点开抽屉没有任何「说法」类内容** |
| 来自搜索 + LLM 的散文 | 5,949 条（95.1%） |
| 来自官方披露 | 官方 69 + 年报 5 = **1.2%** |
| 判官置信度分布 | 85% 打 0.9、13% 打 1.0 → 基本不区分 |
| 被标成「事实」但其实来自搜索网页 | 「晋升发展」742 条 + 「面试难度」527 条 |

### 1.2 三条硬伤

1. **主体错**：「腾讯音乐年终奖 10 个月」——哪个业务线？QQ音乐、全民K歌、内容合作的差异极大。公司级平均值对求职者**没有决策价值**，还可能误导。
2. **结构错**：结论是一段自由文本。**没法索引、没法筛选、没法跨公司比较、没法按口径治理**（想下架某类指标、修某个口径，只能全文匹配）。
3. **强度错**：把「有人在网上说」和「年报白纸黑字」都塞进同一个 `grade` 体系里，且大量搜索内容被标成「事实·公开来源」——**这是对用户的承诺，现在名不副实**。

### 1.3 业务线可抽取性（本次 live 实测，15 家头部公司 44,884 个在招岗）

| 公司 | 标题含业务线信号 | 抽出的真实业务线示例 | 判读 |
|---|---|---|---|
| 蚂蚁集团 | 93.4% | OceanBase / 蚂蚁国际 / 网商银行 / 健康事业群 | 直接可用 |
| 滴滴 | 97.1% | 国际事业群IBG / 网约车平台公司 | 信号强但**噪声重**（混入「27届秋招」「产品实习生」） |
| 快手 | 78.9% | 主站 / 电商 / 生活服务 | 格式规整（`【X】`），但需与无括号版归一 |
| 字节跳动 | 65.9% | TikTok Shop / 抖音电商 / 抖音生活服务 / 飞书 | 5,074 候选词中仅 142 个出现 ≥20 次 → **阈值过滤有效** |
| 腾讯 | 61.0% | 腾讯云 / 企业微信 / 微信小店 / 《三角洲行动》 | 前缀式 |
| 美团 / 小米 | 45.9% | 小象超市 / 闪购 / 无人车业务部；小米汽车(604) | 可用 |
| 网易 / B站 / 腾讯音乐 | 15~19% | 第五人格 / 商业化 | 弱 |
| 百度 / 京东 | 6.7% / 4.4% | —— | **标题里没有**，信号在部门字段与 JD 正文 |

**结论**：业务线是**真实存在、可从第一方数据抽取**的维度，但覆盖不均、噪声真实。
⇒ 必须做成「候选生成 → 阈值 + 停用词过滤 → 落表 → 可人工下架」的**可治理管线**，不是一次性正则。
⇒ 京东/网易已有先例：adapter 层从 `positionDeptName` / `productName` 派生子公司（见 CLAUDE.md）。**原始部门字段优先于标题猜测。**

## 1.5 ⚠️ 范畴的诚实边界（2026-09-03 创始人二次反驳后补，最重要的一节）

> 创始人原话：**「不同业务部门的洞察信息，大部分通过我们的岗位库是拿不到的——工作强度、薪资水平、晋升、面试强度这些用户最关心的问题。而且就算聚合，聚合结论的可靠性也强依赖我们岗位库的规模。」**

**这个判断成立，必须先认下来，再谈方案。**

### 岗位库能答什么、不能答什么（别再自欺）

| 用户关心的问题 | 岗位库能否回答 | 依据 |
|---|---|---|
| 这条业务线在招什么人、多少人、在哪、要什么门槛 | ✅ 能，事实级 | 第一方 39 万在招岗 |
| **稳定性（在扩张还是收缩）** | ✅ **能，且比传闻可靠**：招聘量 30/90 天趋势、岗位批量撤下 | 第一方，可下钻到业务线 |
| 好不好进（竞争度） | ✅ 能：门槛分布 + 岗位在架时长（久招不到 = 缺人） | 第一方 |
| **工作强度 / 加班** | ❌ **完全不在岗位数据里** | —— |
| **真实薪资水平** | ❌ 基本不能：`salary_text` 覆盖仅 1.8%，且是 JD 标注非到手 | 实测 7,123 / 394,839 |
| **晋升 / 职级** | ❌ 不在 | —— |
| **面试难度 / 流程** | ❌ 不在 | —— |

⇒ **用户最关心的四件事里，岗位库只覆盖「稳定性」一件。** 其余三件只能靠「别人说的」，
   而「别人说的」在 v2 被包装成了「事实·公开来源」——**这正是必须治理的谎**。

### ❌ 被证伪的假设：「JD 正文里有公司自述的工作制/福利」（2026-09-03 实测，别再试）

我曾假设：企业官网 JD 正文会写「弹性工作/双休/大小周/股票期权/年终奖」，那属于**公司自述**，可当事实级用来答「强度」。
**实测 388,651 个有正文的在招岗，全部落空**：

| 信号 | 命中数 | 占比 |
|---|---|---|
| 弹性工作 / 灵活办公 | 182 | 0.05% |
| 双休 / 五险一金 | 2,193 | 0.56% |
| 加班 / 大小周 / 单休 | 1,004 | 0.26% |
| 远程 / 混合办公 | 1,098 | 0.28% |
| 股票 / 期权 / RSU | 699 | 0.18% |
| 年终奖 / 十三薪 | 271 | 0.07% |

**根因**：写福利待遇是**第三方招聘平台**（BOSS/智联）的产品形态，企业**官网** JD 只写岗位职责与任职要求。
⇒ 我们坚持「只抓官网」的这条护城河，同时也意味着**福利与工作制信息在源头就不存在**。
⇒ 「强度」这一维**没有第一方路径**，只能靠 ③ 转述或众包。别再回来试这条。

### 聚合可靠性受岗位库规模制约（样本量硬门）

实测在招岗数：字节 20,642 / 美团 4,927 / 腾讯 3,152 / 腾讯音乐 265 / 拼多多 29。
⇒ 同一个统计，在字节能下钻到业务线，在腾讯音乐只能到公司级，在拼多多**什么都不该显示**。

**硬规则（写进展示门与派生层）**：
1. 每个统计**必须带样本量 n**，并在 UI 上显示（「基于 47 个在招岗」）——让用户自己判断可信度。
2. 样本不足即**整字段省略**，不显示 0、不显示「暂无数据」占位以外的任何推断。
   - 业务线级统计：n ≥ 20；公司级分布类：n ≥ 10；趋势类：两期各 n ≥ 10。
3. 禁止用小样本做百分比（3 个岗算出「67% 要求硕士」是噪声不是信息）。

### 因此 v3 的产品定位（三层，措辞与视觉必须分明）

| 层 | 来源 | 能回答 | 措辞 |
|---|---|---|---|
| ① 我们能算的 | 自有岗位库（可下钻业务线） | 在招结构、**稳定性趋势**、门槛、新鲜度 | 「近 30 天新增 47 个岗，较上月 +40%（基于 47 个岗）」——**只给数字，不下结论** |
| ② 官方说的 | 年报 / 交易所 / 招股书 | 员工规模与构成、人均薪酬（粗口径）、上市业绩 | 「据 2024 年报，…」 |
| ③ 别人说的 | 公开讨论（搜索 API） | 强度 / 年终奖 / 晋升 / 面试 | 「有 2 处公开讨论提到…（2025 年）」——**明确是转述，不是我们的结论** |

**业务线这一层的价值要说准**：它让 ① 可下钻（「字节-飞书 在招 47 个后端」远比「字节在招 2 万个岗」有用），
并为 ③ 提供挂载点（当讨论本身点名了业务线时才挂）。**它不解决 ③ 的可靠性问题。**

**③ 变可靠的唯一路径是众包**（用户互惠贡献 + 验证），需要用户量，属 P2，不在本工区。

## 2. 范畴重定义（v3 的骨架）

### 2.1 三种断言强度，区别对待

| 强度 | 定义 | 来源 | 展示措辞 | 能否聚合成公司级 |
|---|---|---|---|---|
| **事实 fact** | 可核验、有官方出处、有明确口径与时点 | 年报 / 招股书 / 官方公告 / JD 明写字段 | 「据 2024 年报，…」 | 能（口径本身就是公司级） |
| **信号 signal** | 从**我们自己的岗位库**算出的观测量，只陈述数字与对比，**不做评价** | 第一方 jobs 表 | 「近 30 天新增 47 个岗，较上月 +40%」 | 能，且可下钻到业务线 |
| **说法 claim** | 公开讨论里的观点 | 搜索 API 摘要（去标识） | 「有 2 处公开讨论提到…（2025 年，指向 XX 业务线）」 | **禁止**。无范围不展示 |

### 2.2 红线（写死在展示门里）

1. **说法类必须带三要素**：主体粒度（公司或业务线）+ 时间窗 + ≥2 个独立来源域名。缺一不展示。
2. **「事实」标签只授予官方来源**（official / official_filing / 第一方派生）。搜索来源一律 claim，不得升格。
3. **不做绝对化表述**：禁止「一定」「必然」「最」「都」。信号类只给数字和环比，不给「该公司在扩张/收缩」这种结论——**结论留给用户**。
4. **业务线差异优先于公司均值**：同一指标若业务线级可得，公司级只做汇总展示，不覆盖业务线卡片。

## 3. 数据模型（「归好类、好索引、好筛选、好治理」的答案）

### 3.1 新表：`insight_subjects`（洞察主体）

```sql
create table insight_subjects (
  id uuid primary key default gen_random_uuid(),
  company_id uuid not null references company_profiles(id) on delete cascade,
  kind text not null check (kind in ('company','business_unit')),
  name text not null,                    -- 「飞书」「TikTok Shop」「OceanBase」
  aliases text[] not null default '{}',  -- 「Lark」「飞书套件」
  origin text not null check (origin in ('derived_title','derived_dept','official','manual')),
  job_count int not null default 0,      -- 当前在招岗数（治理与排序依据）
  first_seen_at timestamptz, last_seen_at timestamptz,
  status text not null default 'active' check (status in ('active','retired','rejected')),
  unique (company_id, name)
);
create index on insight_subjects (company_id, status, job_count desc);
```

`status='rejected'` = 人工判定是噪声（如「27届秋招」），**保留行不删**，下次抽取据此跳过——这是治理入口。

### 3.2 `insight_items` 增列（不破坏现有读写）

| 列 | 类型 | 说明 |
|---|---|---|
| `subject_id` | uuid null | 指向 `insight_subjects`；NULL = 公司级 |
| `assertion` | text | `fact` / `signal` / `claim`（枚举约束） |
| `metric_key` | text null | **枚举**，见 §3.3。有值即可跨公司/业务线索引与比较 |
| `metric_value` | numeric null | 数值 |
| `metric_unit` | text null | `人` / `元` / `月` / `%` / `个` |
| `scope` | jsonb | `{city, function, level, year, bucket}`，**每个键取值受枚举约束** |

`content` 保留为**渲染结果**（人话一句），但由结构化字段生成，不再是唯一真相。

### 3.3 `metric_key` 枚举（第一版，可增不可乱改）

| 域 | metric_key | 断言 | 来源 |
|---|---|---|---|
| 组织规模 | `headcount_total` `headcount_tech_ratio` `edu_bachelor_plus_ratio` `edu_master_plus_ratio` | fact | 年报 |
| 组织规模 | `bu_count` `bu_job_count` | signal | 第一方 |
| 招聘动态 | `hiring_volume_30d` `hiring_trend_30d_pct` `hiring_trend_90d_pct` `open_age_days_median` | signal | 第一方 |
| 招聘动态 | `city_share` `function_share` `bucket_share`（校招/实习/社招） | signal | 第一方 |
| 门槛 | `exp_years_median` `edu_requirement_mode` | fact | JD 明写字段 |
| 薪酬 | `avg_comp_annual` | fact | 年报倒推（带免责） |
| 薪酬 | `salary_range_k` | fact | JD 明写薪资（覆盖 1.8%） |
| 薪酬 | `bonus_months` | claim | 公开讨论 |
| 强度发展 | `overtime_level` `promotion_pace` `interview_rounds` | claim | 公开讨论 |
| 稳定性 | `hiring_freeze_signal`（招聘量骤降） | signal | 第一方 |
| 稳定性 | `layoff_mention` | claim | 公开讨论 |
| 上市 | `listing_status` `revenue_yoy` | fact | 年报 / 交易所 |

**为什么这样就好治理**：想下架「加班强度」这类主观内容 → `delete where metric_key='overtime_level'`；想修人均薪酬口径 → 只动一个 key；想给用户加筛选「只看有薪资数据的公司」→ `metric_key='salary_range_k'` 走索引。

## 5. 验收标准（可量化，缺一不算完）

1. **业务线覆盖**：头部 15 家公司中，≥8 家能抽出 ≥5 个 `job_count ≥ 20` 的真实业务线；人工抽检 100 个 subject，噪声率 < 10%。
2. **结构化率**：新写入的 items 中 `metric_key` 非空占比 ≥ 80%。
3. **承诺诚实**：`assertion='fact'` 的条目 100% 来自官方/第一方；无范围的 claim 展示数 = 0。
4. **可筛选**：能用一条 SQL 查出「近 30 天招聘量增长 >30% 且有薪资数据的业务线」。
5. 四件套 + lint 全绿；迁移在 CI 自动 apply 成功。

## 6. 风险与取舍

| 风险 | 处置 |
|---|---|
| 业务线抽错，把岗位名当 BU（滴滴「产品实习生」） | 停用词 + 频次阈值 + `status='rejected'` 人工下架回路；宁可漏抽不可错抽 |
| 百度/京东标题无信号 | 不强求；这两家走部门字段或维持公司级，覆盖率诚实展示 |
| 存量 5,949 条散文降级后，抽屉内容变少 | 这是**正确的变少**——用假承诺换真诚实；同时 P0-3 的信号类补上新内容 |
| 业务线随组织调整变化 | `last_seen_at` + `job_count` 归零即 `retired`，不删行 |
| 改动面大 | 严格分期，P0 内部再按迁移 → 抽取 → 派生 → 展示 → 治理 顺序推进，每步可独立验证 |
