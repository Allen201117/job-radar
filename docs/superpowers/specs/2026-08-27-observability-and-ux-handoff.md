## 2. 你的第一条主线：可观测性

### 2.1 为什么是它

上一轮所有重大问题的**共同点是静默**——不是没坏，是坏了很久没人知道：

- 浏览器死链审计连续 **13+ 晚**被 90 分钟超时杀掉，日吞吐从 11,800 掉到 4,700，**27 天无人发现**（GitHub 记 cancelled，没人看 job 级）
- `db-report.yml` 上次运行是 2026-07-11，**停摆 6 周**（CLAUDE.md 明写「诊断先跑 db-report」，但它没有 schedule）
- 洞察现查快车道台账 **6/6 永久停在 queued**（workflow 从不回写状态）
- SiliconFlow 欠费返回 **402，而账户级错误判据只认 401/403** → 停摆两天 CI 全绿，每天还照常烧光 90 次搜索额度
- Today 的 feed **永远填满 20 张卡**，所以「该推的漏掉 89%」在任何指标上都看不见

### 2.2 前端实测坐实的一处（最讽刺）

线上 `/admin/health`（2026-08-27 实测，截图证据在本轮对话）：

- 总览写着 **「系统运行 6/6 · 全部正常」**
- 点进「系统运行」，30 天热力图 **29 格里 28 格是红色「处理」**
- 而每个模块卡片、每个指标仍然全部标 **「● 正常」**
- 具体到条目：「职业洞察 · 新增洞察 3 · ● 正常」（当时洞察已欠费停摆两天）、**「刷新/发现 · 产出岗位 0 · ● 正常」（产出 0 也叫正常）**

**同一个页面里，热力图说"天天在坏"，模块卡说"一切正常"。** 判据只看"上次运行有没有报错"，不看"到底产出了什么"。

### 2.3 建议的三层（这是设想，你要出正式方案）

1. **让看板说真话**：产出为 0 不得判「正常」；热力图与模块卡必须同源同口径，不许两套结论；「上次运行成功」和「今日有真产出」是两个不同的信号，要分开显示。
2. **关键链路加真产出告警**：连续 N 天产出为 0 / run 被 timeout 杀掉（**必须看 job 级，run 级会骗人**）/ 任务台账不回写 / 账户级错误。`db-report.yml` 补上每日 schedule 并纳入告警。
3. **补端到端的用户视角指标**：首屏耗时、推荐结果的公司多样性、点击死链率——把 §3 里前端实测发现的问题变成常驻监控，而不是靠人偶然发现。

**方案里要回答**：告警发到哪（本项目边界禁止引入监控大套件、Redis、K8s，所以大概率是 GitHub Actions + 现有的 `ops_runs` 台账 + 看板本身）；哪些阈值；谁来看。

## 6. 工作方法硬约束（血泪教训，违反等于白干）

1. **后端改完必须看前端**——本轮最大的方法论错误。改动影响到哪个界面就打开哪个界面，截图进验收。
2. **先证伪再下结论**。本项目反复出现凭感觉判错：以为「CI 突然频繁失败」（实测 3.4%）、以为「列表只返 13 条所以其余 460 个是死岗」（逐个核验后 460 个全在招）、以为「展示层软 cap 兜住了公司多样性」（打开页面发现满屏字节）。
3. **CI 绿灯 ≠ 有产出；run 级成功 ≠ job 级成功。** 判死活看真实入库条数与 job 级状态。
4. **单测绿 ≠ 逻辑对**。本轮三个最严重的 bug 全是**真实数据对拍**抓到的、单测一个都没发现（用户写「天线工程师」实际在搜「工程师」等）。对拍方法见记忆 `job-radar-matcher-precision-fix`，脚本骨架可复用。
5. **不可逆操作前，核验样本量必须匹配影响面**。要清 447 行就核验 447 行。
6. **指标口径必须诚实**，任何数字写清口径与测量时间。
7. **公开仓库红线**：本仓库是 GitHub PUBLIC。文档里禁止出现本机绝对路径、服务器 IP/主机名、真人姓名/邮箱、任何密钥。
8. 派 Codex 时：spec 要死（文件+行号+改法+验收），沙箱**无网络**，接口信息要先自己 live 验证好写进 spec；它报告的"事实"要自己复核（本轮它说「探活器注册表只有 2 个平台」，实测是 19 个）。
