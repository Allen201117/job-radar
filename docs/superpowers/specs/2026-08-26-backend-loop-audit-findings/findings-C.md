### 根因链（四层，全部实测坐实）
1. **快车道全空转（确诊）**：daily-crawl.yml 快档 CRAWL_DETAIL_CAP=0，而 iguopin parse() 只放行
   _detail_verified 的行（crawler/adapters/iguopin.py:118）→ 快档每轮 fetch 400 行、产出恒 0。
   crawl_runs 证据：国家电网 8/26 五轮 success, reported_total=400, jobs_found=0。岗位实际全部来自
   enrich-crawl 重车道（约 1–3 天一轮）。不致命，但每天烧几十轮请求零产出。
2. **国聘搜索是模糊搜索且硬顶 ~400 行（确诊）**：live 实测任何关键词 total 都截在 390–400；
   返回大量无关公司（搜「国网」夹中国联通，搜「中国石油」夹化学工业出版社）。
3. **match 严格核名把真子公司也杀了（确诊）**：live 抽样 100 行的存活率——南方电网 0%
   （海南电网有限责任公司、鼎和财险这些真南网子公司全被丢）、国网 2%、中国石油 2%、中海油 11%。
   头部央企的子公司法定名不含集团品牌词 → 一进 match 就没了。
4. **就算入了库用户也搜不到（确诊）**：jobs.company 存子公司全称（如「国网国际融资租赁有限公司」），
   品牌词「国家电网」的 bigram（国家&家电&电网）在全称里不存在 → FTS 0 命中。
   北极星 pattern 也是 %国家电网%（lib/must-apply-list.json:200）→ 台账把国家电网记成
   no_active_jobs，尽管它的 iguopin 源里有 2 个健康岗（evidence.matched_job_companies=[] 坐实）。
5. **部分央企核心单位根本不在国聘搜索池（确诊）**：搜「国网浙江省电力有限公司」全名 0 命中——
   国网/南网核心单位走自有门户，国聘上只有边缘子公司。这部分是供给现实，不是我们的 bug。

### 可执行修复路径（关键接口今天已 live 验证）
- 公司维接口是公开的：GET /api/company/index/v1/home?company_id=…（返回官方 nature_cn=国企、
  classify_cn=央企(子企)）和 GET /api/company/index/v1/children-list?company_id=…（集团→子公司枚举）
  匿名可用；/api/jobs/v3/list 匿名 403（不可用）。
- 子公司全名做关键词搜索是干净的：搜「海南电网有限责任公司」首页 10/10 全是该公司。
- 修法：一源=一集团不变，fetch 先用 children-list（或人工核验的子公司清单）展开集团 →
  逐子公司全名搜索 + match 用子公司名集合（而非单一品牌 token）。
- 同步修可见性：给 jobs 侧加品牌归一（子公司名 → 集团品牌 alias 进 search_doc 或 alias 层），
  北极星 pattern 补品牌 alias（%国网% 需人工核撞词，如「中国网安」）。
- 快车道要么跳过 iguopin，要么信任列表自带 contents 正文（iguopin 列表常直接带正文，
  adapter 现在强制逐岗 detail 验证才放行——快道可先信列表、重道复核）。

## C4 长尾 / 产能天花板

- 现状：1,162 家在招公司、sources 1,444（enabled 1,232）；Top-20 占 active 25.9%。
- 需求侧证据太薄：注册用户仅 39 人（互联网 7、金融 2、其余零星）。以此判断「扩到几万家」没有统计依据——
  当前『全面性』短板不是公司数量，而是：① 头部品牌可搜性（C1）；② 行业塌陷（传媒 37%/物流 43%/金融 50%）；
  ③ 个别头部真缺口（拼多多社招、华为正文）。先修这三个的 ROI 远高于铺量。
- 产能天花板（近 30 天实测外推）：
  - 30 天新增源 279（248 enabled），其中两天校招突击 +106；稳态 ≈3–7 个/天；
  - 构成：moka 139 + beisen 105 = 87%——增量几乎全靠两平台猜租户；
  - httpx 自动扩源已枯竭：auto_discover 连续 3 天 checked=80 / produced=0，海外道 0/80；
    浏览器道 2–4/127 每天。合计稳态 ≈3–5 源/天 ≈ 100–150/月，以中型公司为主；
  - gap funnel 浏览器道 8 家/天是必投缺口主吞吐；ats-scrapers 上游 265 候选是一次性增量（必投缺口只直补 2 家）。
  - 结论：现有机制撑不起「万家量级」，但按需求侧证据现在也不需要。若拍板扩量，瓶颈按序：
    候选清单供给（LLM+上游快照）→ 浏览器道配额 → 验收门吞吐。
