## 0. 验证结论(先量后改,已跑)

**源健康不是问题**:1366 个启用源,89.5% healthy(新鲜+有 JD 正文),8.6%(117)零产出、1.1% 陈旧、0.9% 薄卡。零产出集中在多租户 ATS(北森 45 / hotjob 31 / moka 18 / feishu 9)。
⚠️ 但"零产出集中在 ATS" **不能**推成"都是死租户"——正常招聘空窗也长这样;要判死得逐租户探活,别用聚合数推。

**岗位高度集中在少数高产出公司**(下表按"抓到的在招岗数"分组,**不是真实公司规模**):

|---|---|---|---|---|---|
| 北京 33599 | 69.5% | 22.8% | 6.0% | 1.4% | 0.3% |

⚠️ **红队纠错(重要)**:上表证明的是**岗位集中在高产出公司**,**不能**据此断言"真实小厂只占 8-13%"。招聘冻结的大集团、只抓到一个地区的外企,都会落进"低产出层"。所以**现在还没证明**痛点是"小厂库存不足"还是"小厂曝光不足"——这是 v1 第一件要分清的事(见 §7 步骤 1),不能跳过它直接大规模扩源。

**排序集中度不是主因**(推翻了"先做结果分散"的第一直觉):产品真实"newest"排序键是 `first_seen_at desc`(`lib/jobs-store/search.ts:288`),按它测前 50 有 11-31 家不同公司、垄断者是初创/大厂/外企**混合**。(最初用 `last_seen_at desc` 测出"前 50 全顺丰"是排序键选错的假象,已废弃。)

**分层字段已存在但基本是空的、且偏大厂、且不能直接复用**:`company_profiles` 有 `headcount_band`/`funding_stage`/`founded_year`,但:
- `headcount_band`:91% 空,填上的 120 家全偏大——来源 Wikidata(`crawler/wikidata.py`)结构性没有小厂/初创。**最想打的"小厂/初创"标签恰是现有管线填不出的那批。**
- ⚠️ **旧字段不能直接当新轴权威输入**(红队,代码级):① `headcount_band` 有"1000-5000"档,跨新方案的 2000 分界;② 旧富化管线(`insight_backlog.py:217` / `insight-derive.ts:288`)持续按旧口径回写这些字段,复用改语义会被下次富化覆盖;③ `sources.segment` 历史上是按 ATS 类型(greenhouse/lever)批量填 `foreign` 的(`migration 037`),**不是股权核验结果**,只能当线索不能当"已确认所有权";④ Wikidata 人数丢了对应年份,刚富化 ≠ 人数是当前的。→ **新增规范化分类字段,别改旧字段语义;旧字段留给旧消费者。**

|---|---|---|---|

## 1. 问题重定义

"对用户不公平"可能是三件事的组合,但**哪件是主因还没验证**:
1. 没有能筛出小厂/初创的**标签**(需要 Wikidata 给不了的规模信号)。
2. 默认视图被高产出公司**占据**(需先分清:是真库存少,还是曝光被压)。
3. 小厂/初创的**货架空**(岗位 9% 洞察沙漠 + 可能库存本就少)。

## 2. 创始人已拍板的方向

- 分层模型:**底层按 3 轴建(企业性质 / 员工规模 / 发展阶段),前台先合成标签露出。**
- 起手:**先验证 → 再定。**
- 规模信号:**多信号保守式**——硬证据优先 → LLM 兜底 → 实在无据 unknown。**绝不用岗位数硬推规模。**
- P1 重心:**先填小厂供给**(定向抓标准 ATS 上的中小厂),再谈结果分散。

## 3. 分层数据模型:三轴独立、可共存

三个**独立且可同时成立**的维度(红队反例:外企也可以是小团队 → 性质和规模必须能共存,不能互斥):

| 维度 | 新字段(不复用旧字段语义) | 取值 | 证据 |
|---|---|---|---|
| 企业性质 ownership | `ownership_class` | 民营/外资/央企/地方国企/unknown | 股权核验;`segment` 仅作待核线索 |
| 员工规模 size | `size_band_v2` | <100 / 100-499 / 500-1999 / 2000+ / unknown | 硬证据 + LLM 抽取(见 §4) |
| 发展阶段 stage | `dev_stage` | 初创/成长/成熟/unknown | founded_year + 融资事件;初创首版人工精选 |

每维度落地:`值 + 证据URL + 证据日期 + 归属实体范围(集团/法人/经营主体) + 判定状态(已确认/待核实/冲突)`。冲突不投票硬选;跨档区间保留原区间不硬归;证据过期显示"截至某年"。

**标签合成(修正红队指出的自相矛盾)**:标签是**多维度共存**,不是单选 `company_tier`:
- **央国企** = ownership ∈ {央企,地方国企}(独立成立)
- **外企** = ownership = 外资(独立,和规模无关——外企也可小)
- **大厂** = size=2000+ 有硬证据 **或** 命中人工"知名雇主"清单(知名度语义独立于人数)
- **初创** = dev_stage=初创(独立)
- **小厂** = size ∈ {<100,100-499}(**不排除外企/民营**,只看规模)
- **中型(500-1999)= "其他已知规模"**,显式区别于 unknown(红队:民营800人不该落 unknown)
- **unknown** 只表示"证据不足",与"已知但不属这些标签"分开显示

⚠️ 一家公司可同时是"外企+小厂"或"大厂+成熟";前台筛选组合语义按此(勾"小厂"= size 小,勾"外企"= 性质外资,两者 AND)。

### 3.1 v1 不物化到 jobs 列(红队:那是一套跨库一致性子系统,不是加 3 列)
不照搬 `recruitment_category` 的写入时物化。理由(代码级):
- `jobs_db.py` 故意 `_PRESERVE_IF_EMPTY` 防分类降级覆盖;把 tier 放 `_UPDATE_COLS` 会让映射失败/漏页/未匹配**抹空已确认标签**。
- 公司维表超 1000 行必须分页(`crawler/db.py:93`),1449 家一次普通查询静默漏后 449 家。
- app 侧还有独立枚举列写入器(`lib/jobs-store/write.ts`)。
- 画像可独立更新,岗位分类却等重抓才刷 → 同公司新旧岗位长期挂不同标签。

**v1 做法(更轻)**:标签存**小型带版本的 company→标签映射表**(公司数量级 ~1449,不是 40 万岗)。筛选时把标签解析成**已核验公司名集合**,在 SQL 候选截断**之前**用精确 `company = any(...)` 过滤(jobs 已有 company 索引 `jobs-db/schema.sql:356`),同一份 conds 复用算 total(对齐 `formatMatchTotal` 口径)。
**只有当集合增大后实测性能不足,才**同步一张 HK 公司维表做同库 join;**再不足才**考虑逐岗物化。先量后改。

### 3.2 公司实体对齐(红队:同步越成功,错标可能越严重)
`company→tier` 默认两边 company 指同一主体,代码不保证:画像按 `sources.company` 建、岗位用 `raw.company or sources.company`、adapter 可返子公司名(`normalizer.py:217`),洞察匹配还含去后缀/子串(`insight-match.ts:36`)。
→ v1 建**明确公司键 + 核验过的名称映射**;每条规模证据标"集团/法人/经营主体"范围;`source_id` 辅助关联但**集团招聘源含多子公司,不无条件继承集团标签**;模糊匹配只产"待核验候选",不直接写权威分类;326 家无画像公司要定义补齐流程。

## 4. P0 命门:LLM 是"证据抽取器",不是"猜测打分器"(红队核心修正)

⚠️ 红队:"公司名+域名+JD 片段 → confidence≥0.8" 站不住——域名不是官网正文,JD 通常不含员工总数和融资阶段;模型自报的 0.8 **不等于** 80% 正确率;`chat_json` 只是调模型,洞察那套引文/判官门**不会自动继承**。

信号优先级(高→低,**宁可 unknown 不错标**):
1. **硬证据**:已有明确人数(年报/官网披露)→ 映射,状态=已确认(注意旧 headcount_band 跨档问题,原始区间保留)。
2. **官方所有权线索**:`segment`=soe/foreign → 作**待核**ownership,不直接升级已确认。
3. **LLM 证据抽取**(SiliconFlow,复用 `insight_engine.chat_json` + `llm_budget` 成本闸,降级模型禁思考模式):
   - 先抓公司官网"关于我们/团队介绍/融资公告"**原文**,让 LLM 从原文**抽取**人数区间/融资日期/主体,**强制返回可核验 URL + 原文引句**;抽不到明确证据 → unknown。**不让模型凭公司名猜。**
   - 上线前做**分层盲测**(单列"稀疏资料小厂"和"集团子公司"两组),报**准确率 + 覆盖率 + 无法核验比例**三个数,不只报准确率;"全库对拍"需独立答案源,**不能拿第二次 LLM 回答当标准答案**。
4. 都无 → unknown。

**双向误判控制**(每个判据写下会往哪两方向错 + 各一计数验收,不许只报净值):小→大(猛招小团队/跨城重复/母集团人数套子公司)、大→小(招聘冻结/只抓一区/A轮信息过期)→ **岗位数一律不作规模信号**。

## 5. P1:填小厂供给(重心)+ 结果分散(并行)

### 5.1 填小厂供给——新建 SME 候选台账(红队:不能直接复用 gap_funnel)
代码级缺口:`gap_funnel` 队列被必投清单限定(`gap_census.py:343` 读 `must_apply.by_industry`,`--company` 只过滤清单);`generate_targets.py:129` 优先"中大型/知名/多岗"(方向相反)且两个 auto-discover workflow 里 `AUTO_DISCOVER_LLM=false`;auto-discover 快车道验收 ≠ `gap_funnel.run_acceptance_gate` 的完整门。
**做法**:新建**薄的 SME 候选台账**(公司名 / 核验过的官方域名 / 名单来源 / 规模证据 / 退避状态),**别把小厂塞进必投清单污染北极星指标**。抽出通用"入口发现 + 准入验收"复用。
- 候选发现 vs 岗位来源**分离**(codex):VC 被投名单/孵化器/园区名单/搜索 = 只给**线索**;入库岗位必须是公司官网/官方 ATS 的**逐岗详情页**过质量门;投资机构自建聚合列表**不算**被投公司官方 ATS。
- 分界线是"有没有标准 ATS + 逐岗页",不是公司大小。首批全部 **disabled 试抓 → 有效岗回读 → 详情核验 → 才 enable**。
- 小厂天然间歇开关岗(招满半年零产出),零产出监控区分"死租户/入口迁移/访问失败/正常空窗",别一律判死;浏览器抓取有超时史(`enrich-crawl.yml`),加北森/Moka 源不自动=稳定供给。

### 5.2 结果分散(便宜、并行,但按页面处理)
红队:分散逻辑**不能只改 `filterAndRankJobs`**——Today 已有公司配额(`lib/opportunities/grouping.ts:130`),Jobs 要在**分页前**稳定分散且**不能把溢出岗位永久丢弃**(否则"加载更多"点不完)。必要不充分:若真库存少,分散只治标。

## 6. 分层洞察

复用现有引擎按 tier 供给。**初创洞察边界**:可说"某日宣布某轮融资/JD 写明期权",不可推"能活18个月/期权价值/不加班";查不到就显"暂无可靠资料"。微型公司洞察沙漠是现实,标签整体保证有供给,不承诺每家都有。

## 7. v1 优先级(改为"精选试点验证",红队的 80% 路径)

不先改几十万条 jobs。v1 按此跑通闭环、拿真实数验证,再决定要不要上重基建:

1. **先分清库存 vs 曝光**:对 2-3 个目标城市+岗位方向,抽样核验"低产出层"里到底有多少是真小厂(vs 冻结大厂/单区外企)。这一步决定后面到底该扩源还是该改曝光。
2. **精选 50-100 家候选小厂**(现有库存 + 外部名单),核验实体/规模/官方岗位入口,写进 SME 候选台账。
3. **小型带版本 company→标签映射**(不逐岗物化);筛选时解析成核验公司名集合,SQL 截断前精确过滤 + 复用条件算 total;性能实测再说。
4. **结果分散**按页面接(Today 复用现有配额 / Jobs 分页前分散不丢溢出)。
5. **LLM 证据抽取 + 分层盲测**产出准确率/覆盖率/无法核验率三数,再决定放不放进自动管线。

**P2**:央国企补齐(仅 26 源,先校归属再补入口)。**P3**:精选已核验初创 + 其洞察。

**成功判据(试点指标,非现状)**:目标城市+方向下"持续提供可投岗位的**已核验小厂**家数" → 再看"前 20 不同公司数"、曝光、收藏/投递转化;官方详情有效率(jd_url 门)不下降;每 tier 的 healthy 源/有效岗/洞察覆盖进 `ops_runs` 台账 + 告警。

## 附录 C:采用的权威分层定义 + 数据可得性(2026-09-15 调研,直接抄标准)

**规模轴改采工信部口径(替代 §3 里我自拟的 <100/100-499/… 档)。** 来源:工信部联企业〔2011〕300号《中小企业划型标准规定》(现行有效,统计局国统字〔2017〕213号数值一致、仅更新行业代码)。分微型/小型/中型/大型,**按行业门类**,判档用「从业人员 且 营业收入」(微型是"或")。与本产品最相关门类的门槛(人=人数,营收=万元):

| 行业门类 | 小型上限 | 中型区间(人 / 营收万) | 大型下限(人 且 营收) |
|---|---|---|---|
| 软件和信息技术服务业 | <100人 或 <1000万 | [100,300) 且 [1000,10000) | ≥300人 且 ≥1亿 |
| 信息传输业(含电信/互联网) | <100人 或 <1000万 | [100,2000) 且 [1000,100000) | ≥2000人 且 ≥10亿 |
| 零售业 | <50人 或 <500万 | [50,300) 且 [500,20000) | ≥300人 且 ≥2亿 |
| 批发业 | <20人 或 <5000万 | [20,200) 且 [5000,40000) | ≥200人 且 ≥4亿 |
| 工业(采矿/制造/电热气水) | <300人 或 <2000万 | [300,1000) 且 [2000,40000) | ≥1000人 且 ≥4亿 |

⚠️ **大型门槛因行业差异极大**(软件 300 人 vs 信息传输 2000 人),所以**不能跨行业套统一人数线**;且工信部要「人数+营收」两者,缺营收只能给"近似档"并显式标注,不得包装成"工信部标准"。

**其余轴的采用口径**:
- **央国企**:国资委央企名录(2025-07 起 100 家,需定期同步官网,会变);国有控股=国有股权>50%。**判据是股权,不是公司名**——「XX集团/控股」不构成判据。
- **大厂/中厂/小厂(互联网语境)**:无官方标准 → **人工白名单 + 规则兜底**,不做纯财务阈值自动算(逐年浮动、易被挑战)。
- **初创**:无统一权威定义 → **产品自定义业务规则**(如成立≤5年且融资≤A轮),文档须标"自定义口径,非行业标准"。独角兽:CB Insights(≥$10亿,无年限)vs 胡润(≥$10亿且成立≤10年)**口径打架**,展示前须选定一家并注明。

**数据可得性(决定每个标签能不能准确做)**:我们的数据源(公开招聘页)基本拿不到营收/股权/融资/成立日期。因此:
- ✅ 现在能准确做:**央国企**(名录+segment=soe)、**大厂**(白名单)、**上市**(funding_stage)、🟡**外企**(segment=foreign 弱证据+已知外企)。
- ❌ 缺数据只能多数 unknown:**中厂/小厂**(工信部要行业+人数+营收)、**初创**(要年限/融资)。要做准需接**公司工商信息源**(成立日期/参保人数/股权),属独立数据接入决策。
- 复核方法/逐行业完整数值/来源清单见调研原文(researcher 2026-09-15)。

## 9. 最大风险(红队,实现者视角)
系统全做完才发现:**最需要识别的小厂恰好没有可核验证据**,最后只能在"筛选按钮没货"和"高置信错标"之间二选一。→ 所以 v1 必须先跑步骤 1+2 拿到"可核验小厂到底有多少"这个数,再投入基建。
