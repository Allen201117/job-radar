# 求职雷达产品与后端审阅意见

审阅取证：2026-09-06—07；汇总成稿：2026-09-08。性质：本 Session 审阅结论的汇总与整改建议，未实施业务修复、迁移或部署。

**综合评分：60／100。产品有清楚的价值方向，也已有真实供给和可用闭环；但岗位库、洞察库还不能持续保证“信息可信、符合条件、值得行动”。当前最应该投入的是两套数据的全生命周期，以及匹配正确性。继续增加数据量、生成内容或展示功能，不能替代这项工作。**

Next.js、Python、PostgreSQL、Supabase 和 GitHub Actions 仍可以承载下一阶段改进；这不意味着现有数据流、双库边界和定时生成方式已经最优。局部缺陷应直接修复，结构调整应通过同条件对照决定，不能因为已经跑通就保留，也不能因为系统复杂就整体重写。

## 1. 审阅依据与结论边界

需求依据为 [PRD](../../PRD.md) 与[外部审阅指引](2026-09-06-external-review-brief.md)。审阅追问的是：用户能否更省时间地找到自己符合条件、仍可申请的官方机会，并获得有根据的信息，判断“值不值得投、什么时候投、怎么投进去”。岗位数量、脚本数量、模型通过率都不是这个目标本身。

本意见汇总[第一轮审查](2026-09-06-first-principles-review.md)与[全生命周期及架构续审](2026-09-07-data-lifecycle-review.md)。分工包括文档与数据子 Agent（Terra）、跨文件代码审查子 Agent（Sol，高思考）；主 Agent 负责产品判断、架构取舍和最终整合。本次汇总另由文档、数据子 Agent 交叉核对结论修订和数字口径。

- **已确认缺陷**：代码存在可达错误路径，部分已通过真实函数配合模拟 I/O 复现。它证明问题存在，不自动证明线上影响比例。
- **待补证据**：有风险或缺少验收记录，需要定向核验；例如缺恢复演练记录，不等于没有备份。
- **候选架构**：提出替代方案及否定条件，尚未对拍，不能称为最佳方案。
- **历史观测**：生产快照主要为 9 月 6 日，调度日志核对为 9 月 7 日 02:20 UTC；均不是报告阅读时的实时状态。

首轮应用基线为 `1154512`，本次汇总核对到 `2e22a3f`。期间其他会话已移除职业路径页、补入 `/insights` 和 `/programs` 页面埋点，并增加新用户 Today 热门岗位与快捷设置。因此这些不再列为待办。相关体验、部署成效，以及同期地理分类和项目制投递扩展，本次未重新完整验收，不据此自动调整评分。仍在的风险包括 Today 读取个人上下文失败后被当作空值处理。

## 2. 按产品需求评分

以下权重和分数是本轮证据下的专业判断，不是用户满意度、推荐准确率或成功率。权重突出岗位事实与洞察决策价值；不按功能数量计分。同一根因只安排一份整改，按不同的用户结果解释评分，不把同一个 bug 在多项中反复累计扣分。

| 产品要求 | 权重 | 得分 | 已经成立的部分 | 主要扣分依据 |
|---|---:|---:|---|---|
| 岗位真实、新鲜、可投 | 30 | **22** | 官方源、详情 URL 质量门、正文富化、逐岗核验均有实际实现 | 撤岗身份删除后可能回潮；正常页面可能误判关闭；未知结果可能显示为刚核验；部分采集不完整 |
| 按用户条件准确筛选匹配 | 20 | **14** | 已有硬条件、偏好合并与可解释排序，明确冲突不能靠加分抵消 | 前置召回与后置分类不一致；上下文查询失败可能静默丢掉用户约束；正文语义存在漏召回路径 |
| 洞察可信，能帮助判断是否值得投 | 30 | **12** | 已区分事实、岗位信号、公开经验，并有出处与展示门 | 招聘趋势有错误外推；多域名不等于独立证据；适用范围和推断强度未充分约束；帮助决策的增量未被验证 |
| 搜索、浏览、收藏、投递体验 | 10 | **7** | 主链可用、官网直跳、后台校验不阻塞点击，已有收藏与反馈 | 有可触发的慢搜索路径；尚缺完整浏览器与冷暖场景的体验验收 |
| 持续更新、纠错与恢复 | 10 | **5** | 抓取、探活、生成、清理有调度和业务输出 | 失败推进成功时间、跨主题换代、半发布及出处更新不一致、人工裁定可被刷新绕过、缓存撤回无期限；恢复能力缺验收 |
| **合计** | **100** | **60** | | |

归属说明：I3 的发布与出处一致性统一计入持续更新项。F9 中“正文语义漏召回”与“大量候选搬运导致慢路径”是两条不同问题，分别归匹配和体验；不会把一次慢请求再次当作匹配不准确的证据。

**对产品的评价：值得继续做，但目前应按需要持续运营校验的早期产品管理。**已有能力足以支持真实使用和验证价值；还不足以让用户长期放心地把筛选和判断完全交给系统。洞察是最能形成差异、也最需要补证据的一项，不能仅靠岗位数量来弥补。

## 3. 两个核心底座到底缺什么

| 生命周期 | 必须守住的合同 | 当前主要断点 |
|---|---|---|
| 岗位：发现 → 采集 → 归一身份 → 核验发布 → 刷新 → 撤岗 → 清理 → 恢复 | 同一岗位有稳定身份；只有足够证据才能确认状态；失败不冒充成功；清理后仍记得关闭与用户关联 | 身份随正文清理消失；观测、富化与确认混用；分页结果与完成状态不一致；历史与恢复不闭合 |
| 洞察：主体/主题建队列 → 取证 → 核验 → 发布 → 换代 → 展示 → 纠错/过期 → 重试 | 每个结论有对应证据及适用范围；发布与来源完整提交；失败只重试未完成部分；人工纠错跨刷新生效 | 公司级时间戳掩盖主题失败；局部成功替换整家公司旧内容；多步写入留下半成品；撤回不能及时传到所有展示面 |

洞察有三类输入：岗位观测、官方或结构化资料、公开经验。岗位库是重要输入，但不能替代全部洞察来源。两库共同需要的是**稳定身份、证据、明确状态、原子发布、可接续任务和可生效纠错**；匹配召回及请求性能还需要另外修正。

下文 R01–R09 是可分工的整改工作包。F1–F10 对应第一轮报告，I1–I5 对应生命周期报告，便于回查反例与代码行号。建议字段与状态均是设计提案，不代表仓库已经存在这些 API。

## 4. 具体优化建议与验收

### R01｜先保证岗位不会“错杀、假新鲜、死后重生”

**优先级：P1，确定缺陷。对应 F1/F2/F3。**用户可能看到已经撤销的岗位，也可能错过仍在招聘的岗位；探测失败还可能被包装成“刚确认在招”。

涉及：`crawler/jobs_db.py`、`crawler/enrich.py`、`crawler/enrich_backlog.py`、`crawler/audit_dead_links.py`、`lib/jobs-store/write.ts`、`lib/opportunities/freshness.ts`、`jobs-db/schema.sql`、`.github/workflows/purge-expired.yml`。

具体改法：

1. 保留轻量的岗位身份和关闭记录，正文允许按存储策略回收。身份至少关联 canonical/官方职位标识、招聘轮次、确认关闭的原因与证据；关闭记录写入和物理清理必须同事务成功，不能事后补记。
2. 将探测结果统一为 `alive / dead / unknown`，拆开“尝试时间”“确认开放时间”“正文更新时间”。403、429、超时、半截页和解析失败只影响重试，不提升确认覆盖。
3. 浏览器按站点业务码、岗位错误容器或明确关闭信号判断。普通正文出现 `404123`、页脚出现“活动已结束”，不能关闭岗位。
4. 列表再次出现只更新观测，不推翻已确认关闭。重新开放必须有绑定该岗位的新正向证据；官方复用职位编号时，明确识别新招聘轮次，保留历史关联。
5. 枚举 Python、应用端、后台审计等全部写者，统一接入数据库状态转换约束。保留现有“空字段不抹正文”“已有 expired 不被列表刷活”等保护；关键转换记录与状态一起提交，普通耗时日志仍可旁路。

**验收：**关闭→清理→旧列表重抓不生成新 active；真实重开可恢复；并发清理与 upsert 不绕过身份；旧收藏/已投递关联仍有效；未知不变已确认；正常正文和真正关闭页都判对。影响存量的关闭/清理逐行保留依据，不凭少量抽样操作整批。

**代价与迁移：**增加小量身份存储和显式重开流程。历史混写时间戳先标注证据不足，不能全部信任或全部清空；已删除证据也不能推测补造。

### R02｜让采集“完成多少、还欠多少”可计算，并统一请求预算

**优先级：P2，确定缺陷；发布模式为候选改造。对应 F5/F6。**有的后页失败会丢掉前页，有的部分完成仍记 success；扩量和重试可能争用未被统一约束的请求预算。

涉及：`crawler/run.py`、`crawler/adapters/`、`crawler/robots.py`、`crawler/jobs_db.py`、抓取与探活 workflows。

具体改法：

1. 将自写分页迁入已有共享分页合同，保留已成功页并明确 `partial`；统一记录上游总量、已读数量、截断原因、完整性、游标与结束时间。首页失败、成功为空和部分完成分别处理。
2. 列表缺席撤岗继续要求已验证的全集能力。完整空源进入独立审计，由额外完整抓取或逐岗详情确认；补控制流时同时补小源保护，不因单轮零条清空存量。
3. 让请求并发、最小间隔、列表上限覆盖 adapter 内部线程及重叠作业；对同 host 竞争使用共享限额或明确串行策略。遵守 Retry-After，预算不足留待办，不能记抓取完成。
4. 用通配符、大小写及 query 的正反夹具修正 robots 匹配，并验证实际请求所用策略。不要未经语义验证只替换 parser。
5. 在协议能力不同的少量来源上试验“列表观测→候选→证据足够才发布”，优先核验目标需求缺口、新增变化和到期岗位。列表本身证据充分的来源可直接过门；不强制所有岗位追加详情请求。

**验收：**第二页失败仍保留第一页且不执行 absence；成功空、未知空、小源零条均有对照；嵌套并发及重试不突破预算；比较唯一相关可投机会、最长等待、完整率和成本。列表不变仍要到期核验，不把“没来得及验证”统计成“没有岗位”。

**代价：**峰值吞吐可能下降，候选等待可能延迟新岗。因此第 5 项必须对拍，不能为减少假 active 造成不可接受的真实机会漏失。

### R03｜统一匹配口径，读取失败不能悄悄丢掉用户条件

**优先级：P1，确定缺陷。对应 F8/F10，并承接 F9 的召回边界。**用户设置校招，前置筛选却可能漏掉后置认可的岗位；偏好查询失败又可能被当成没有偏好。

涉及：`lib/jobs-store/opportunities.ts`、`lib/jobs-store/search.ts`、`lib/opportunities/eligibility.ts`、`lib/opportunities/service.ts`、`app/today/page.tsx`、`app/api/opportunities/route.ts`。

具体改法：

1. Today 与 Jobs 复用已存储的招聘分类及明确性字段，并传到后置判断。仅缺字段时走同一后备规则；当季届别使用生产函数，不在审查脚本里写死年份。
2. 将画像、偏好、动作、来源读取结果明确区分为“成功有值／成功为空／失败”。缺来源元信息不能自动升级成可信手工源。
3. 读取失败时保留可证明适用的最近成功上下文，或返回可重试的明确降级状态；不能静默放宽排除词、地点、阶段，也不能把临时失败引导成新用户重新填表。
4. 按逐字段覆盖原则保留用户手动筛选优先；行业、公司、关键词兜底与画像按真实生产逻辑一起回放。未知学历或届别保持透明，不改成一律排除。

**验收：**冻结岗位集上，前置召回覆盖后置可展示集合，最终展示不混入明确冲突项；包含管培生、正文才说明职能、旧届别、无标签、排除词等正反例。分别注入各上下文读取失败，确认条件和用户动作不会失效。辅助画像回放不能替代完整生产链验收。

**代价：**故障时可能明确显示重试或降级，优于给出看似正常却违背用户条件的结果。跨请求缓存必须绑定用户及上下文版本。

### R04｜把洞察改成“按主题接续、完整发布、局部换代”

**优先级：P1，确定缺陷。对应 I1/I2/I3。**一次失败或额度耗尽，可能让公司长期不再进入常规刷新；一个主题成功，又可能撤掉其他未更新主题。条目与来源分开写，还会留下半发布状态。

涉及：`crawler/insight_backlog.py`、`crawler/insight_engine.py`、`app/api/insights/admin/route.ts`、洞察表及迁移。

具体改法：

1. 按公司/主体、主题和阶段保存 `last_attempt_at / last_success_at / next_retry_at`，结果区分有结果、成功查无、失败、预算延后、部分完成。只有真正完成才推进相应成功 TTL。
2. 预算耗尽记 deferred，恢复预算后接续；网络失败短退避；成功查无使用独立空结果 TTL。不要把未搜索过的主题封存 90／180 天，也不把预算不足累计成公司质量失败。
3. 外部取证完成后，再用一次数据库事务发布“条目版本＋各自证据＋关联＋对应主题换代”。先准备候选，不先插 active 再逐步补来源；失败整体回滚，重试使用稳定幂等键。
4. 新主题版本只替换它覆盖的旧主题和范围。其他主题保留最近可信版本及真实时间；全部计划主题都有明确结果才记录整轮完成。
5. 官方资料更新正文、等级或 origin 时，同步更新对应出处。每份引文只能绑定真实支持它的来源，不能把来源 A 的一句话复制成来源 B 的证明。

**验收：**零预算不调用搜索且不推进成功时间；第一主题成功、第二主题失败时，只换第一主题；在每个写入步骤注入异常，均不留下对外可发布的半成品；重复运行不重复发布，正文和出处版本一致。现有展示门继续保留，不能以它能挡住部分孤立条目为由接受残留。

**代价：**需有限 schema 与写入入口调整。模型和网络调用放事务外；只让同库关键写入原子化，不假设岗位库和洞察库之间存在跨库事务。

### R05｜洞察先证明“能支持什么”，再决定生成什么

**优先级：P1 修正错误派生；证据模型调整需对拍。对应 F4 及架构续审 §9.3。**同样的真实发岗量，仅关闭旧岗，当前计算就可能显示“扩张、HC 充足”；两个转载网站也可能通过域名数量门。

涉及：`lib/insight-derive.ts`、`app/api/insights/route.ts`、`crawler/bu_signals.py`、`crawler/insight_engine.py`、`lib/insight-verification.ts`、洞察证据与展示模型。

具体改法：

1. 统一即时洞察与后台信号的统计定义。历史趋势基于可回查观测及相同覆盖，记录采集批次、来源范围、统计日期和计算版本；缺基线显示未知，不输出“平稳”。
2. 删除缺证据的 HC、竞争强弱及投递窗口断言。岗位统计可说明“本产品覆盖范围内观测到的变化”；源扩张、抓取截断或旧岗退出不能直接解释成企业招聘预算变化。
3. 将证据观察及版本作为长期记录，生成文案作为可重建结果。保存必要短摘录、地址、发布时间、采集时间、适用团队/地区/职级、原始来源或转载线索及冲突；遵守既有去标识与不保存完整 UGC 的边界。
4. 将“引文是否支持原句”“原始来源是否独立”“是否适用于目标岗位”“是否仍有效”分别核验。模型的自报置信度未经独立标注校准，不能当外部真实性概率。
5. 先做可直接核验且与决策相关的主题，同时保留注明范围的经验观察。比较同一证据集的直接展示与生成摘要；页面先给已有证据和缓存解释，新增生成异步进行。

**验收：**等量发布但老岗关闭不制造扩张；源覆盖变动、缺基线和真实增减均可解释；同稿转载不算两份独立观察；团队/职级不匹配不外推；独立但相反的经验保留分歧。域名反例只证明单道门的边界，不代表整条生成链必然发布或线上大量转载。

**代价与否定条件：**可自动总结的内容可能减少。若摘要没有改善理解、反而扩大误导，就取消该主题的自动总结；若新增证据结构成本明显高于收益，则缩小主题范围，不能靠多生成掩盖证据不足。

### R06｜让人工纠错跨刷新生效，撤回能到达每个展示出口

**优先级：P1 裁定持久化，P2 缓存传播。对应 I4/I5。**旧条目被下架，不代表新 UUID 或定时 upsert 不会再次发布同一内容；用户重开抽屉也可能一直看到缓存旧版。这些有代码与隔离反例支持，尚未证明某条线上申诉内容已复活，也未量化线上影响数。

涉及：`app/api/insights/dispute/resolve/route.ts`、`app/api/insights/admin/route.ts`、`crawler/insight_backlog.py`、`crawler/bu_signals.py`、`lib/insight-client.ts`、`lib/insight-availability-cache.ts`、公司抽屉和对比页。

具体改法：

1. 区分到期、被新版本替换、人工下架、申诉成立。人工裁定关联主体、主题、具体断言及证据版本，所有生产者发布前检查；参考已有主体 rejected 的保留机制。
2. 同证据换措辞不算新事实，也不能只按文本哈希拦截；新相反证据走明确复核。避免永久封禁整家公司或整个主题。
3. 申诉状态与条目下架同事务提交，不能出现“申诉已成立、内容仍 active”。发布、撤回、到期统一触发服务端失效。
4. 浏览器响应带版本与到期时间，设短 TTL，在重开和恢复焦点时复核；错误响应不长期缓存。缓存策略须覆盖抽屉、对比、洞察列表和详情，不能只修一个入口。

**验收：**人工否决→自动刷新，同证据不能重发；新证据可复核；故障重试不产生半裁定。建议以“联网且页面打开时，撤回 60 秒内在各展示面生效”为试运行目标，纳入集成验收；这是建议目标，不是当前保证。

**代价：**增加版本检查和少量刷新请求。来源临时打不开不等于事实为假，必须区分网络未知、原始证据撤回、出现矛盾和历史资料仍有效。

### R07｜减少请求时搬运和重算正文，先证明不漏再提速

**优先级：P1 测量与改进，结构方案待验证。对应 F9。**默认匹配搜索最多读取 28,000 个含正文的候选，再在应用端筛选排序。已有缓存和部分下推，但冷请求仍可能付出高成本。

涉及：`lib/jobs-store/search.ts`、`lib/jobs-store/opportunities.ts`、`lib/opportunities/`、`jobs-db/schema.sql`、岗位写入与特征生成入口。

具体改法：

1. 先拆开认证、数据库连接、SQL、数据传输、应用计算和页面可操作时间，分别测冷暖路径。9 月 6 日一次搜索 GET 用时 25.175 秒只能证明慢路径可触发，不能当 P95 或全归因于数据库。
2. 岗位内容变化时，计算可复用、带版本的分类与职能等特征；查询使用可索引硬条件和轻量特征，最后给展示页补正文。结合执行计划与数据量调整查询和索引，不先改连接池或堆缓存服务。
3. 正文独有的职能、届别、否定条件必须有等价特征或受控全文检索兜底。偏好与随日期变化的规则仍在请求时正确应用；新特征未就绪保留兼容路径。
4. 用同一冻结岗位集、真实生产上下文构建方式做影子比较，先检查召回与排序，再看字节和延迟。不能只删 summary 或收紧标题换取速度。

**验收：**硬条件反例零回归，正文语义不丢，候选截断和 top-k 相关性有对照；同时报告冷暖 P50/P95、各段耗时、传输字节与维护成本。实施前固定延迟目标及容许的新岗延迟，达不到召回要求则撤回新路径。

**代价：**特征版本、重算和兼容读增加维护工作。只有复用收益和端到端提升得到证明，才扩大覆盖；暂没有证据要求上向量库、Redis 或新搜索服务。

### R08｜把“任务在跑”升级为“欠账可追、失败可续、数据可恢复”

**优先级：P1 补恢复验收；持久任务按缺口分阶段收口。对应 F7 及生命周期共同约束。**现有业务输出证明调度真实存在，但不证明所有实体及时完成，也不证明故障后可恢复。

涉及：各抓取/洞察 workflows、`crawler/ops_runs.py`、工作队列选择、`lib/admin-health.ts`、`docs/runbooks/jobs-db-production-safety.md`。

具体改法：

1. 统一记录计划、已完成、失败、延后、最老等待和下次到期；workflow 成功、业务完成及数据库回读分开。岗位治理按唯一岗位和源计算，洞察按主题完成率计算，不用重复尝试数充当覆盖。
2. 优先给高价值缺口、未确认及到期实体分预算，量出实际等待与容量再扩 worker；不能把各分片上限相加当日处理能力。
3. 对会中断丢进度的链路引入持久待办、短租约、幂等和对账。Actions 可继续执行；租约过期可重领，重复执行不重复发布。无需为此立即引入完整工作流平台。
4. 先核验已有备份，再在隔离环境完成恢复演练。检查岗位身份/关闭记录、用户反馈关联、洞察有效版本/来源/裁定的一致性，并记录实际可恢复时点和恢复用时；若现有策略不够，再补备份频率、保留期与步骤。
5. 跨库派生带输入批次和版本，可幂等重算；关键跨库通知用持久待办与对账，不靠一次 best-effort 事件冒充可靠同步。

**验收：**中断后只续未完成部分；预算恢复后任务能再次入队；重复领取不重复产生业务结果；积压和超期可见；恢复后有业务回读记录。缺恢复记录是证据缺口，本意见不声称云端没有备份。

**代价：**新增任务状态和对账成本。普通性能日志无需全部强事务；专用执行器或数据库边界调整由等待时间、故障恢复与总成本决定。

### R09｜用真实用户决策验证价值，不能拿库存除以动作数

**优先级：P2，与整改后的验证并行。属于证据补齐。**当前有使用痕迹，但没有足够证据解释“没看到、没合适的、看到了但没帮助”各占多少。

涉及：`lib/track.ts`、事件入口、Today/Jobs、洞察消费入口、用户反馈与运营汇总。

具体改法：

1. 在已有页面埋点上补可关联的机会曝光、查看洞察、打开官网、保存/忽略及原因；按用户、机会、时间窗关联，并记录采集失败的可观察性。`/insights` 页面埋点已补，不重复建待办。
2. 点击只记点击；官网打开不能推定申请完成。`saved/ignored/applied` 当前状态与历史事件分开，用户自报投递也单列，不使用“库存÷当前 applied”推导转化。
3. 在明确目标人群中开展一轮建议为 14 天的小规模观察：核对发现了哪些此前不知道的有效机会、节省哪些搜索步骤、洞察具体改变了什么判断，以及错误/漏失原因。
4. Today 作为行动入口、Jobs 作为探索和纠偏支撑，是待验证的产品取舍。岗位详情与项目制公告各自按真实申请方式验收，不能把公告入口冒充逐岗详情。

**验收：**能区分触达、供给、匹配、可信度及产品增量问题；至少能回溯一条完整决策链。小样本用于发现问题和验证机制，不直接宣称市场需求成立或整体转化提升。

**代价：**需要少量真实用户反馈和人工核验。已确认的后端真值错误应先修，不能把“再观察用户”当成推迟修复的理由。

## 5. 技术栈与架构的正式取舍

原则是先修确定缺陷，再比较职责划分；物理表、数据库、服务数量服从实际收益。下面的“优先试验”均未获得最优认证。

| 设计决策 | 优先比较的方案 | 如何判断与否定 |
|---|---|---|
| 岗位发布 | 当前直接入 active 后治理，对照候选＋按证据发布；高量源加入新增/变化/到期增量核验 | 同目标范围、同核验预算，比不可投曝光、真实机会漏失、新岗延迟和总成本。证据充分的源可保留直接发布；排队显著错失机会则不采用统一两阶段 |
| 洞察生产 | 固定周期公司主题生成，对照证据增量＋缓存解释；优先自动化可直接核验的高价值主题 | 同证据集比较正确理解、范围外推、来源覆盖和总成本。生成摘要无增益或更误导时，保留证据展示、取消该主题自动总结 |
| 检索计算 | 请求时大量正文判断，对照有版本的写入特征＋轻查询＋最终页补正文 | 完整语义下比较召回、相关性、冷暖延迟与特征维护成本；无法控制漏召回就不能以速度批准 |
| 任务执行 | 各脚本选队列＋cron，对照持久到期待办＋租约＋幂等；Actions 可继续做执行器 | 比漏执行、最老等待、恢复用时和运维成本；已由现有链充分保证的部分不重复建设 |
| 数据库边界 | A 保留权威库分布并补合同；B 查询侧投影必要来源/状态；C 经常联合处理的公开业务数据同库，认证仍托管 | 同时测跨库耗时/失败、状态传播、恢复及未来维护成本。B 要承担同步陈旧，C 要承担迁移/权限/故障集中；没有依据立即合库或永久锁定分库 |

应保留的有效设计：官网直跳与异步探活、明确冲突的匹配硬门、未知透明、canonical 归一和 URL 质量门、空值不覆盖富化正文、已有 expired 黏性、jobs 写入失败不回退到另一空库、已有缓存及共享分页、HTTP 优先与已有退避。建议改的是缺失合同，不是把这些保护一并推倒。

全量微服务化、更换语言、购买新基础设施、全面停爬或继续按源数量扩量，目前都没有足够比较证据支持。项目体量与预算需要实测，不用固定 DAU 或连接池乘法直接决定迁移。

## 6. 落地顺序与角色分工

以下是后续实施安排，不代表本次已启动修改。主负责人统一业务合同与验收，子任务按模块边界并行，避免各写者重新定义“成功、关闭、发布”。

| 阶段 | 工作包 | 责任划分 | 进入下一阶段的条件 |
|---|---|---|---|
| 1：停止错误确认与错误替换 | R01 状态/判死与清理保护；R03 口径/读取失败；R04 成功时间/主题替换；R05 去掉错误外推；R08 恢复证据核验 | 岗位后端、匹配后端、洞察后端独立实现；数据子任务只读核对影响面；主负责人审查语义 | 对应反例变成通过的正反测试；线上影响与迁移范围有只读基线；无批量猜测清理 |
| 2：补齐跨阶段合同 | R01 稳定身份；R04 原子发布；R06 裁定与撤回；R02 完整性/预算；R08 接续与恢复演练 | 数据层负责约束与事务，生产者接入；前后端共同负责撤回；运维负责隔离演练 | 清理→重抓、失败→接续、发布→纠错→刷新等跨链验收成立；全部写者纳入 |
| 3：证明结构调整有收益 | R02 候选/增量；R05 证据与解释；R07 轻量检索；按瓶颈比较队列/双库 | 主负责人定对照与取舍；实现任务隔离；独立审查角色检查漏失和故障面 | 在相同范围和预算下有质量、时效或成本净收益；有版本兼容与回退方案 |
| 4：证明用户得到了价值 | R09 真实观察；沿同评分表复评 | 产品负责人归因，数据角色核口径，工程回读真实链路 | 能解释获得/错失的机会和洞察作用；有实际反馈及稳定运行证据 |

阶段之间允许无依赖工作并行，例如性能分段测量和恢复资料核验可提前；不能先扩大新架构覆盖，再补正确性验收。每次上线应带迁移范围、失败回退与上线后业务回读，代码或测试通过不等于生产修复成立。

## 7. 从 60 分到 80 分，应交付什么

下面是沿原权重设置的阶段目标，合计 80 分，不是修完指定数量的 bug 自动加 20 分。只有相应证据成立才重新评分。

| 维度 | 当前 → 阶段目标 | 加分所需证据 |
|---|---|---|
| 岗位真实、新鲜、可投 | 22 → 27 | 稳定身份与三态成立；目标来源分层的真实逐岗核验能证明可靠性；关闭、重开、缺席、清理正反路径通过，且不以漏掉真岗换准确 |
| 准确筛选匹配 | 14 → 17 | 同生产上下文、当季参数的完整回放；硬条件不丢、正文语义不漏；前后置一致，暂时读取失败不放宽用户条件 |
| 洞察决策价值 | 12 → 20 | 统计不越界；来源与范围可回查；证据独立性和冲突有标注验收；真实用户能说明洞察怎样帮助或改变判断 |
| 使用体验 | 7 → 8 | 登录、新用户、无结果、错误恢复、搜索及官网跳转的浏览器验收；冷暖端到端测量达到事先约定的目标 |
| 更新、纠错、恢复 | 5 → 8 | 网络失败、额度不足、中断和重复执行后可接续；主题换代正确；人工裁定持续生效、撤回有期限；隔离恢复有业务回读 |

统一验收方法：固定同一批目标公司/岗位方向、用户上下文、观察时间窗与成本上限；参考集加入从官网独立核验的机会，不能只从本库抽样而漏算库外机会。同时测“错误放进来”和“正确挡在外面”。确定性红线夹具要求零回归，线上质量比例必须带样本量、分层、时点和未知项。迁移先小范围运行与回读，再扩大，失败回退到已验证版本。

**建议立项主题：岗位与洞察可信生命周期整顿。**第一批产出应是可执行的状态合同、修复后的反例、迁移与恢复验收，以及同条件架构对照结果。这些才能把 60 分提高为可复查的产品质量。
