## 3. L1：价值成立到哪一步

### 3.1 产品真正交付的单位

用户要的是：**在有限时间内，找到自己符合条件、仍可申请、此前不知道或来不及追踪的机会，并能安心进入下一步。**“官方链接”降低信息来源和跳转的不确定性；“个人偏好”减少筛选工作；“及时发现与核验”降低漏投和空跑。缺任何一项，都可能只剩一个更干净的职位列表。代码主链确实对应这一价值：`app/today/page.tsx:43–84` → `lib/opportunities/eligibility.ts:230–257` → `app/today-client.tsx:217–255`。

因此它有明确的需求机制，但“值得用户改变习惯”**尚未被证实**。本轮没有用户访谈、对照组或外部投递回执，不能代替用户下肯定结论，也不能从低动作数判死需求。

### 3.2 当前行为实际说明什么

近 7 天 `events` 共 965 条，其中 `job_click` 127、Today 打开事件 68、`opportunity_official_opened` 13、洞察抽屉打开 12；`radar_open` 与 `radar_feed_opened` 各 68，不能相加当 136 次访问。一次 `job_actions` 快照仍为 viewed 522、ignored 69、saved 62、applied 12；其中近 7 天创建且仍存在的 applied 状态有 7 条。

这些信号证明有人在使用，不证明有多少活跃求职者持续获益。不能用事件次数相除直接报转化：尚未按用户、曝光、会话和时间窗关联，且事件是 best-effort，`app/api/events/route.ts:8–42` 写失败仍返回 204；`lib/track.ts:268–285` 是异步上报。点击官网事件也不是官网成功打开或真实完成申请的回执。

**判据应分三步：**用户没有进入 Today，优先检查触达/入口；用户进入但没有相关可投机会，检查供给、召回、硬门和核验；用户获得相关新机会仍不愿继续使用，才更有力地质疑产品增量价值。当前日志尚不足以完成这条归因。

### 3.3 岗位与洞察的关系

双层架构有合理性：确定的岗位事实与有来源、有时效、有不确定性的公司信息分开，避免推测污染岗位资格。但“两层存在”不等于护城河成立。当前 active 洞察 14,538 条，assertion 分布是 signal 10,824、claim 3,336、fact 378；大量信号来自自有岗位派生。来源覆盖、时间序列、纠错积累和用户实际采纳才可能形成长期差异，条数和 LLM 总结本身不能证明壁垒。

本轮没有复现旧报告中的“无来源经验条目普遍展示”：experience 且 assertion 为空为 0；排除 signal 后 sample_size≥5 的 2,891 条中，0 个有效绑定来源为 0、1 个为 9、至少 2 个为 2,882。这里按 `deidentified=true` 统计，不等于独立 publisher 数，也没有人工逐条验证原文。更明确的新缺陷在招聘趋势推断，见 F4。

**只能保留一个模块：保留 Today。**它最直接承载“少花时间处理有效机会”的承诺；Jobs 保留为 Today 的探索与纠偏能力，属于支撑。此为产品取舍建议，不是假称现有行为已证明 Today 优于 Jobs。

**现在最该做的一件事：开展一次有人工真值的 14 天 Today 用户验证。**选择确有求职任务的自愿用户，逐条标注“相关 / 真实开放 / 是否新发现 / 是否节省工作”，记录回访与官网行动；先修复本文确定的数据真值错误，以免用受污染的“核验通过”作验证标准。示例规模 8–12 人是小样本学习方案，不是统计显著性承诺。按用户和求职方向报告分布，预先约定产品负责人愿意继续投入的门槛，不在看到结果后改口径。

## 4. L2：产品形态的取舍

Today 的硬门、可解释理由、新鲜度和反馈移出队列已经实现；“唯一主产品”的信息架构收敛没有完成。转型 spec `2026-06-23-personal-opportunity-radar-pivot-design.md:123–158` 原要求五项导航并降低 Path；当前 `components/NavbarClient.tsx:29–46` 有八项，`:257–264` 又重复提供“我的”。另一方面，当前注释明确将洞察库升为平级，这是后续方向变化；不能只拿六月文档宣布九月实现错误。

| 模块 | 服务的决策 | 本轮建议与反向成本 |
|---|---|---|
| Today | 今天优先处理什么 | 主入口；把质量和首次有效机会作为首要验收。过度压缩数量可能制造假空队列，应保留原因解释和搜索出口 |
| Jobs | 主动探索、调整方向、查目标公司 | 保留。删掉会失去纠偏与验证推荐的通道 |
| 校招 / 项目制投递 | 对应届身份、招聘窗口、公告与报名入口作判断 | 保留明确差异，不把公告入口包装成逐岗 JD。其时效价值不能由总访问量低直接否定 |
| 洞察库 | 核查目标公司、辅助选择 | 保留来源和不确定性；先修派生偏差、补消费归因，再扩大生产。弱证据自动生成越多，可能让信任更差 |
| 职业路径 | 判断下一步目标与优先次序 | 优先降为辅助入口或小范围验证，暂缓独立扩建；不是直接删除，因为缺少模块采纳数据 |
| 值得投 / 已投递 | 比较机会、记录推进状态 | 保留；把“打开官网”“自己标记已投递”“拿到面试”分别表达 |
| 我的 | 维护目标和个人资料 | 收到账户入口，减少重复；保证偏好修改仍易找到 |

八项是否太多，取决于是否承担八种常用决策，而不是注册用户是否只有 80。现有优先级叙事相互冲突、部分入口重复，足以支持一次轻量收敛；没有证据支持全站重设计。

**最该补的一项能力是可关联的机会曝光与决策记录。**现有 events 不是空白，缺的是同一次机会曝光的关联标识、当时的匹配/核验版本、未点击原因与后续动作归因。先在 Today 上形成一条可解释的记录链，采集最小必要信息，避免把完整简历或岗位正文重复写事件。这比再加一条通用扩源链更直接服务价值验证。`CompanyInsightDrawer.tsx:118–138` 只有抽屉打开，`lib/track.ts:301–315` 页面白名单遗漏 `/insights`，也说明洞察消费不能由投稿/申诉数代表。

## 5. L3：技术路线是否有效、是否最优

### 5.1 自建采集：保留主力，撤回“唯一方案”的绝对结论

| §5.1 论据 | 判定 | 证据及边界 |
|---|---|---|
| 国内 ATS 厂商 API 全部逐企业授权 | **存疑（全集断言不成立）** | [Moka 官方鉴权](https://people.mokahr.com/docs/guide/authentication.html)明确机构 API Key；北森/飞书公开资料不足以证明全国厂商全集。客户管理 API 与公开租户招聘接口也须分开 |
| 国内数据商都无官网逐岗链接 | **存疑** | 本轮没有可验证的供应商全集、合同或字段样本，不能断言全部没有；也未取得满足当前定位、成本与覆盖要求的替代总 feed |
| Google for Jobs 国内不可用，因此不能替代 | **地区可用性未证实；替代结论仍无支撑** | [Indexing API](https://developers.google.com/search/apis/indexing-api/v3/using-api)是向 Google 通知页面变化，不是消费全库职位的 API。不能把它当采集替代，无需依赖未经本轮验证的地区判断 |
| 只有国聘、搜索找入口、用户众包三条补充 | **不成立** | 还存在企业授权 feed、公开 ATS board API、页面 [JobPosting](https://developers.google.com/search/docs/appearance/structured-data/job-posting)；覆盖有限，不能直接替代全链 |

第五条路线是**与目标企业建立授权职位 feed**。它能完全替换合作企业的抓取，代价是合作获取、接口与数据质量维护；对一人低预算产品不宜以全国 BD 为主线。公开 [Greenhouse API](https://www.greenhouse.com/api) 和 [Lever Postings API](https://github.com/lever/postings-api) 已证明部分来源不必解析页面；仓库 `greenhouse.py`、`lever.py` 也已经这样做。Lever 的公开 postings 与需要鉴权的管理 API 不可混淆。

建议的采集顺序：现成公开 API → 可验证的结构化页面/API → 必要的浏览器 → 人工/合作补缺。托管浏览器或托管采集服务可以替换执行环境，不能替代归属、全集、逐岗链接、撤岗和用户相关性的判断。“69 个 adapter 应否存在”不能按文件数裁决，应按平台协议差异和持续提供的有效机会裁决。

### 5.2 保留当前栈与存储边界

Next.js/TypeScript 负责应用与用户交互，Python 负责批量网络 I/O 与解析，PostgreSQL 保存事实、索引与状态；Supabase 管认证和小型业务表。这与当前成本和维护条件相容，没有发现必须改语言或改框架的证据。jobs-store 边界、写失败不回退空 Supabase jobs、同城部署、模块级 JWT/JWKS 缓存都应保留。

两数据库的代价是真实存在的：跨库关联不能依赖外键和单事务，岗位删除会影响行为归属，应用同时依赖两条网络路径。因此要定义稳定岗位身份、用户动作快照和失败策略。下一步应完善这些契约，而非把两库强行合并或新增第三个服务。

岗位检索继续使用 Postgres bigram/tsvector + GIN。[PostgreSQL 17 文档](https://www.postgresql.org/docs/17/textsearch-indexes.html)支持 GIN 作为文本检索优选索引；它并不保证任意中文召回、过滤和排序方案都快。**“45 万行、2 GB RAM 能撑多久”没有可诚实给出的日期或 DAU 数。**磁盘 relation 大小超过 RAM 不代表工作集全要驻留；需要测代表性 SQL、缓存冷暖、返回行数、网络传输、JS 评分与并发。

下一步顺序：先补分段计时与 EXPLAIN，再决定候选投影/索引/物化、缓存与连接预算。若峰值证实连接等待而 DB CPU 有余量，评估 PgBouncer；若热查询读盘主导，评估内存或索引；若写入健康而读流量独立饱和，再考虑只读副本。PgBouncer transaction mode 还需检查 session 状态、prepared statements 等语义，[官方特性表](https://www.pgbouncer.org/features.html)不能省略。没有本轮实测，不给“必省多少毫秒”“支持多少 DAU”的数字。

### 5.3 GitHub Actions：成本合理，可靠性需由应用补齐

[GitHub 官方计费](https://docs.github.com/en/billing/concepts/product-billing/github-actions)说明公开仓库的标准托管 runner 使用免费；这不是所有 runner、存储或服务能力无限。[schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)明确高负载可延迟甚至丢弃。39 个 workflow 本身不是故障；需要的是每种任务有负责人、预算、互斥/租约、checkpoint、补跑和完成判据。

本轮 19 个已完成 liveness workflow 的 created→updated 最长 140.4 分钟，551 个 adapter job 最长 88.9 分钟，**没有证据证明已发生四小时自重叠**。但 `liveness-sweep.yml:16–20` 实际 02/10/22 UTC 是 8/12/4 小时间隔，注释“8h 等距”错误；330 分钟单项上限和缺少 workflow concurrency 允许未来重叠。可补互斥与可恢复进度，不能只加 `cancel-in-progress: true`，否则可能反复取消最慢源。也不宜仅把时间错开当作全局连接预算。

Vercel 当前套餐不能由 `maxDuration=60` 推断。若产品进入收费/商业运营，应核对实际套餐与 [Hobby 使用边界](https://vercel.com/docs/plans/hobby)，不在本审查中自动升级或购买基础设施。

## 6. L4：必须改的具体缺陷

以下是可复现的代码行为或明确的证据缺口。P1 表示优先处理；P2 表示应修但不应挤掉核心真值问题。条件反例不等于本轮已量化线上受损行数。

### F1 · P1：删掉撤岗身份后，同一死岗可作为“新岗位”重新出现

**证据：**`purge-expired.yml:41–45` 删除全部 expired；`jobs-db/schema.sql:83` 的 `job_events.job_id` 为 `ON DELETE CASCADE`，CLOSED 事件一起消失。`crawler/jobs_db.py:379–419` 查不到 canonical 就新建 UUID；`lib/jobs-store/write.ts:101–154` 同一路径。sticky expired 只保护尚存旧行，无法保护已物理删除的身份。

**反例已执行：**模拟 purge 后 canonical 不存在，同 URL upsert 返回 `created`，走 fresh INSERT。结合已知会夹带关闭岗的列表，形成“判死 → purge → 列表再见 → 新 ID active”的可达链。旧 saved/applied 的 `job_snapshot` 保住历史文本（`app/applied/page.tsx:61–83`），但旧动作不再与新 ID 对应，可能重复推荐。没有据此声称线上所有新增都是回潮。

**修法：**永久删除大正文可以保留，但 canonical 身份/关闭证据必须独立保留，或先延缓硬删除直到该机制就绪。墓碑写入与删除必须在同一事务中成功，失败整体回滚；upsert/reopen 与 purge 之间还需唯一约束和原子冲突处理，不能“先查后写”引入竞争。只有新的明确在招证据才能显式 reopen。墓碑失败不能继续删除，历史已级联删除的事件不能靠推测补造。

**双向验收：**关闭岗列表重现不新建；真实重新开放的岗位可按明确证据恢复；并发 purge/upsert 不绕过身份约束；用户历史与新鲜度不重置。代价是小表存储和 reopen 路径，换取避免循环探活、误报新增与动作失联。

### F2 · P1：浏览器全页匹配“404”会把正常岗位误判为撤岗

**证据：**`crawler/audit_dead_links.py:66–71,273–287` 对整个 body 优先匹配裸 `404`、`not found`、`已结束`，再检查岗位标题；`:351–366,408–410` 将 dead 写 expired，随后被 purge 删除。

**反例已执行：**岗位标题“软件工程师”，正文“软件工程师 职位编号 404123，负责推荐系统研发，欢迎投递。”，实际判 `('dead', '404')`。这是确定的分类错误，不是伪造一个远端 404 故障。

**修法：**按站点绑定专用错误容器/精确标题/业务码；普通正文或页脚出现关键词不能判死。增加正常正文含 404、页脚活动结束、反爬页、半截页、真正关闭页的对照。对将被批量改变状态的每一行留可审计依据，再决定处置；不凭抽样清一整批。

**双向代价：**保守判定可能多保留少量未知死岗，但能减少不可逆误删。目标不是固定“凑两个条件”，而是信号明确绑定当前岗位，并区分站点异常与岗位关闭。

### F3 · P1：把“探测失败/不确定”写成“刚确认仍在招”

**HTTP 路径：**`crawler/enrich.py:223–240` 的 Amazon/Apple 对非 404/410 状态也可正常返回空串；空串同时表示已确认的无正文 alive 与未知响应。`crawler/enrich_backlog.py:183–214` 在已有 summary 时把空串记 alive，写 `enrich_checked_at`。

**浏览器路径：**`audit_dead_links.py:391–410` 将导航异常标 unsure，却和 suspect/alive 一样盖核验戳。`lib/opportunities/freshness.ts:43–74` 将 24h 内此字段当 verified，`lib/jobs-store/read.ts:247–253` 也用它算健康覆盖。两条反例均已隔离执行。

**修法：**统一 `{verdict: alive|dead|unknown, reason, summary?}`；分开 attempted_at、confirmed_open_at 与关闭证据。unknown 用于退避，不用于展示核验通过；补正文与证明开放也是两件事。应用 `lib/liveness-client.js:235–243` 已有三态，两个 API 对 unknown 不写回，是可复用的正确契约。

**双向验收：**403/429/500、解析失败、半截页不增加确认覆盖；真活岗可以更新确认时间；真死岗保留证据；未知源不因无确认时间被立即重轰。修复后“已核验率 / alive 数”可能下降，这是纠正口径，不应为了指标好看回退。历史混写的时间戳不可自动全部认真或全部清空。

### F4 · P1：幸存岗位构造了虚假的招聘扩张，还进一步推断 HC

**证据：**`app/api/insights/route.ts:97–145` 读取当前 active 岗位并实时派生；`lib/insight-derive.ts:277–291` 用当前仍 active 的岗位倒推两个 30 天窗口新增量；`:309–339` 将其写成“招聘扩张、HC 较充足”，缺少前窗时还默认“平稳”；`:343–424` 输出到招聘洞察。`CompanyInsightDrawer.tsx:465–471` 展示信号。

**反例已执行：**两个窗口各真实发布 30 个岗位，初始趋势 0%。仅把旧窗 27 个岗位关闭，未增加任何发岗，输入当前 active 后变成 **+900% 扩张、HC 较充足**。只有当前窗时，trend=null 却输出“平稳”。

后台 `crawler/bu_signals.py:243–281` 已改用历史快照，并明确不靠 first_seen 窗口凑趋势；两条派生链没有同步。即便换快照，也只能描述“在本产品覆盖范围观测到的在招岗位数量变化”，还要控制新增源/截断/下架规则变化，不能等同企业招聘预算或竞争强度。

**修法与验收：**统一派生语义，缺基线输出未知；移除 HC/进入窗口宽窄断言，区分样本统计与建议。测试等量发布但老岗关闭、源覆盖突增、截断、缺基线、真实新增/减少两个方向。代价是洞察文字少一些，收益是用户不再被计算偏差误导。

### F5 · P2：分页异常与终态不一致，已有保护没有覆盖全部 adapter

**全集扫描：**至少 12 个自写分页模块在后页 `raise_for_status()` 抛错后丢掉本轮前页结果：Amazon、Antgroup、Bilibili、BYD、Hikvision、JD、Meituan、Mihoyo、Pinduoduo、Tencent campus、Tencent Music、Vivo。逐文件行号见附录；真实 `_fetch_board` mock 第 1 页 100 行、第 2 页失败，直接抛异常。

`paginate_all` 已有“保留前页 + complete=false”，应迁移或复用其契约。但 `run.py:435–438,510–534,616–624` 又会把明确 incomplete 的结果记 success，主计数并不诚实；coverage 字段已保存，watchdog 明细可发现，不能称全系统完全看不见。

另有 `run.py:440–444` 完整空列表提前返回，绕过 `:491–505` absence。仅对已证明全集、adapter 显式支持、`fetch_complete=True / reported_total=0` 的情况应进入专门审计路径。**完整空源不得仅凭单轮列表自动 apply**，必须有额外独立完整抓取或逐岗 detail 证据，以及空源专门闸。现有 `jobs_db.py:319–328` 在 active<8 时不执行比例闸，不能用“已有 50% 保护”替代小源验收。控制流修复不等于授权清零，正文/身份删除还须满足 F1。

**双向验收：**后页失败保住新增前页但不判全集；首页失败仍 failed；成功空源与未知空源区分；partial 状态和 ops 计数一致。代价是用户能看到部分更新而非等待整源成功，必须保留完整性标记，不能把 partial 当撤岗依据。

### F6 · P2：robots 规则与实际请求预算没有统一兑现

`crawler/robots.py:71,114–126` 匹配时丢 query、没有 `*`，还将路径转小写；反例 `Disallow: /*.pdf$` 对 `/jobs/cv.pdf` 错误放行。源码声称按 Google 规则，而[官方说明](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec)明确通配符与路径大小写语义。先按夹具修正语义，不未经验证直接换一个同样不支持所需语义的 parser。

`CRAWL_MAX_JOBS` 只有 10 个 adapter 模块读取，不是真正全局降档。`run.py:598–607` 的同 host 源队列不能约束 BYD 10 线程、米哈游 6、HotJob 4、国聘 3 的源内请求；也不提供跨 workflow/runner 的 host 预算。已有请求间隔、Workday Retry-After 与字节退避值得保留。本轮没有证据声称已经造成封禁。

**修法：**统一列表上限、host 请求并发和最小间隔，尊重 Retry-After；robots 失败采用明确短时退避与缓存策略；实际 HTTP/浏览器 UA 与策略选择要可追踪。成本是峰值吞吐下降和小量共享封装，收益是降档真的有效、故障重试更可控。验收同时比较完整率、成功用时、429/5xx、唯一有效新机会，不只比较每分钟请求数。

### F7 · P1（运维证据缺口）：恢复能力还没有可引用的验收记录

`docs/runbooks/jobs-db-production-safety.md:5–15,40–119` 仍将快照/PITR/恢复演练标为未验证；本轮读取 [Issue #3](https://github.com/Allen201117/job-radar/issues/3) 仍 OPEN，验收项未勾选，最后更新为 2026-07-11。七月限时例外不等于今天通过验收。

`docker-compose.jobs-db.yml:1,12–21` 是本地 PoC 的命名卷，不是生产备份；本地 `backups/` 文件未被 Git 追踪，未读取其内容，不能当恢复证据。**这些事实不证明云端一定没有备份。**必须补取已有备份元数据并完成一次隔离恢复；若未配置，再制定最小加密快照、保留期、恢复步骤、RPO/RTO。先证明能恢复，再讨论读副本和大规模扩容。实际基础设施操作须另行实施，本次没有执行。

生产快照 active 455,584；有效正文 active 439,822（96.54%）；薄卡 15,762。24h 内列表见过 321,212，这个数不是“今日新增”。根据同一年龄查询的累计桶换算：

2026-08-30 07:32:06Z 至 09-06 07:32:06Z 的 `ops_runs.liveness_sweep` 共 640 条，checked 1,475,190、台账 alive 1,449,099、expired 11,422。**98.23% 的 alive 是当前代码记账结果，不是人工验证准确率**，且同一岗位可重复计数。Workday 占 checked 687,694；WT 135,417、失败 7,616；HotJob 105,143；国聘 20,350、expired 4,296。台账量大与长尾久未确认可以同时成立。

静态浏览器预算：底盘 7,200 次/日、新岗 1,200 次/日、必投 1,600 次/日，都是尝试上限，存在重叠、超时和 unknown，不能加成“每天确认一万个唯一岗位”。HTTP 同样不能拿 35×50,000×3 当兑现容量。

近 7 天 `crawl_runs` 全量 46,035 行：success 41,619、partial 1,013、failed 553、skipped 2,850、unfinished 14；created 122,790 是写入动作，受补历史、去重与 F1 影响，不能全部解释为企业新发布。`ops-watchdog` [run 34014201740](https://github.com/Allen201117/job-radar/actions/runs/34014201740) 自身 success 但报 15 项发现，说明监控有用且“绿灯”有多种含义。

## 8. 匹配与前端：规则正确性和候选数据形态仍需修正

硬门比单一加权更合适：岗位职能、明确地点、求职阶段和排除词不应被技能重合“加分补回来”；缺学历/届别标签也不应自动判不符合。保留已知冲突排除、未知透明展示、岗位职能优先，以及可解释排序。不使用 LLM 决定排序、暂不引入向量库的边界仍成立；本轮缺陷主要是事实语义和可验证的规则/召回问题。

已只读取得 28 份真实画像的匿名回放输入。其中 11 份没有 target_roles，17 份有角色；12 份有地点；阶段为空/实习/校招/社招为 4/7/12/5。51 条偏好记录中 39 条至少有角色、关键词或目标公司。画像字段空不等于 Today 必空，可能有偏好、关键词、关注公司兜底，必须按应用实际合并逻辑判断。

### F8 · 必须改 / P1：Today 前置校招规则漏掉后置规则认可的岗位

`lib/jobs-store/opportunities.ts:249–300` 预筛只查标题/job_type/URL 的少量词，未采用 `recruitment_category/recruitment_explicit` 主路；候选列 `:69–77` 也没有带回这两个字段。Jobs 已有物化分类主路和 NULL 兜底（`lib/jobs-store/search.ts:168–191`），Today 却仍在候选前后重复做不同的判断。

合成“管培生”岗位对校招画像，真实 `computeMatchFacts/checkEligibility` 可过门，前置谓词却不匹配。辅助 psql 曾得到校招 42,921 个中 1,328 不匹配预筛、实习 21,583 个中 0 个不匹配，**但该计数不能作为生产漏召回率**：除 TLS 边界外，查询还写死排除 grad_class<2026，而 `currentGradClass()` 在九月返回 2027。它包含生产本来应排除的旧届别，当前实际影响面仍未知；可独立复现的代码反例成立。重核须导入同一生产谓词和当季参数，并同时检查正反方向。

修法是让 Today 复用物化分类并把字段传到后置门；NULL 才走一致的后备规则。正文截断不能抹掉已确认分类。验收必须证明前置候选条件覆盖后置可展示集合，同时验证没有把实习/社招或过期届别混入，不能只断言 SQL 中出现某个关键词。

### F9 · 建议优先改 / P1：候选过宽与漏召回并存，默认 Jobs 搜索有 25 秒路径

17 份有角色条件的匿名真实画像完成 `buildRecallSql(7天,1800) → jobs → computeMatchFacts → checkEligibility → scoreOpportunity` 核心回放：共召回 14,281 个候选，1,341 个过硬门；方向不符 8,411、地点不符 2,262、阶段不符 1,554、行业不符 684，2/17 触及候选预算。**9.4% 是候选通过比例，不是最终推荐准确率。**该批属于待严格 TLS 重核的辅助证据；还缺 sourceMeta、真实动作、critical/group/hydration 等完整链。28 份输入均未关联用户偏好表的 keyword/company，11 份未执行者恰好也缺 roles，不能算真实 Today 的空队列率。

代码层 `opportunities.ts:385–405` 的 company/cityNew 层只优先排序方向命中，仍召回大量不相关岗位。相反，“战略项目岗、正文明确产品经理”的合成岗位后置可过门，`search_doc` 却不含 summary（`jobs-db/schema.sql:198–205`），只有角色且无公司/城市旁路时也可能漏。简单收紧标题或者无限抬高预算都会付出另一侧的精度/成本代价。

限量测试账号 GET 的一次观测：

| 请求 | 状态 | 审查端总耗时 | 响应体字节 | 解释 |
|---|---:|---:|---:|---|
| `/today?__timing=1` SSR | 200 | 6.960s | 378,482 | HTML 流读取完成，不能当首张可操作卡时间 |
| `/jobs` SSR | 200 | 0.823s | 207,207 | 页面壳快，后续数据请求仍可慢 |
| `/api/opportunities` | 200 | 4.039s | 54,289 | 内部 total 1.944s：recall 1.254s、sourceMeta 244ms、compute 434ms、hydrate 4ms；capped，main 20 |
| `/api/jobs/search?limit=10&sortBy=match` | 200 | **25.175s** | 16,337 | 返回 10 条且 capped，长路径可触发；不等于 P95 |

这些是 fetch 读完的响应体字节，不是完整浏览器总下载量或压缩后线路流量。采样约在 2026-09-06 21:57–21:58 CST，四个请求只覆盖一个测试账号与一次访问序列。

`lib/jobs-store/search.ts:23–52,456–528` 的默认匹配预算可拉 28,000 候选且带 summary；只有进程内五分钟缓存。源码历史计时提示结果搬运昂贵，但本轮没有对这个 25 秒请求做 SQL/传输/JS 完整分段，**不能断言其中每一秒的根因**。

建议先将招聘分类、职能与过滤所需的受控特征落成一致的数据字段，SQL 形成更小、稳定、有召回保证的候选，然后按展示页回补正文；保留正确的完整 SQL+params 缓存键。不要把所有正文直接塞进通用搜索向量，也不要为了缩 payload 直接删掉后置判断所需信号。验收对比漏召回、误召回、capped、人工 top-k 相关性、响应字节与冷暖耗时的双向变化。

### F10 · 必须改 / P1：小表查询失败被当作没填偏好，静默改变匹配条件

`app/today/page.tsx:43–84`、`app/api/opportunities/route.ts:19–43` 并行查询偏好/画像/动作/打开状态，仅取 data 而不检查 error；Jobs 页和 API 也有同类路径。超时或权限错误可能被解释为空偏好/空 actions，用户的排除词失效、已处理岗重现或被引导重新填写资料。

`lib/opportunities/service.ts:73–108` 捕获 sources 查询错误后返回缺项；`eligibility.ts:199–205` 对缺 sourceMeta 不视为禁用且使用 manual 新鲜度口径。来源查询异常因此可能改变资格，而不只是少一个说明字段。

应把“确实零行”和“查询失败”分开；保留上一次成功上下文并明确显示降级，或返回可重试错误。缺来源证据不得自动升格 manual。需要针对每张小表与元数据失败做运行时注入测试，验证返回结果不会悄悄丢掉个人约束。代价是失败时不再总返回看似正常的队列，收益是用户看到的含义与事实一致。

### 其它明确边界

Jobs GET API 在 `app/api/jobs/search/route.ts:32–71` 明确允许匿名，而页面 middleware `:60–85` 要登录；本轮未发现应用代码级限频。公开岗位内容本身不是泄露，但昂贵匿名查询需要明确预算和产品授权边界。建议 P2：若不提供公共 API，统一鉴权；若有意开放，保留公共入口并配额、限制输入与并发、统一错误码，避免直接返回 e.message。不能仅凭没有登录就称漏洞已被利用。

自定义域 `/api/jobs/stats` 另一次匿名请求 200，TTFB 4.849s，总 4.853s，响应 66 字节。主线程原 Vercel 域超时、浏览器控制桥反复超时/空白，后续 HTTP GET 成功提供了反证；不据前者宣称生产全面故障。上述测试均未形成 p50/p95，未执行浏览器交互和点击后的异步链，也未测峰值连接占用。

现有 `scripts/match-eval/eval.js:64–80` 用 30 天而当前生产 7 天，缺 sourceMeta 并允许覆盖 freshness；`scripts/verify-opportunity-recall.ts:32–69` 又手抄旧查询。它们不能直接称“等同真实用户体验”。建议评测统一导入生产构造器，支持匿名画像和完整上下文，原始输出放不入库目录；不把本轮简化回放当新的完整 E2E 基线。

性能下一步应补同一部署、同一画像的冷暖样本，分别测认证、SQL、传输、JS、SSR、首张可操作卡，并同步取连接 waiting/active/idle。17 个画像的本地 psql median 5.632s/P90 32.481s 含审查端握手和传输，不可移作 Vercel 线上延迟。

## 9. 建议改与不建议改

### 建议改

| 顺序 | 建议 | 正向收益 / 反向成本 | 验收方式 |
|---|---|---|---|
| 1 | 按活跃求职目标的缺口分配扩源、刷新和核验预算 | 补用户要的机会、减少低价值重复；长尾更新变慢，保留主动搜索/点名补缺 |
| 2 | 在 ops 中区分 attempted/confirmed/unknown、完整性、唯一岗位与逐源等待 | 看见语义失败和长尾；增加少量指标维护，先覆盖关键链路 |
| 3 | 北森 route 缓存覆盖与实际执行路径台账 | 已验证租户减少浏览器；错误 route 可能错链，必须逐租户比对 ID/总量/详情 |
| 4 | 按协议拆 china_ats，保留兼容入口 | 降低平台间回归面；纯拆分不能承诺性能收益，先保行为与契约测试 |
| 5 | 加小型协议夹具和跨模块回归，少量限频 live canary | 提前发现改版/字段变更；夹具会过期，需记录采样时间和版本 |
| 6 | 收敛当前决策文档与导航主叙事 | 避免 Agent 按过时碑文继续扩建；保留历史因果，不要求把所有文档再重写一遍 |

北森 321 个 enabled 是候选范围上界，不能当可新增迁移数，已有多少走 HTTP 本轮未测。可行顺序是已验证 route 的稳定复用、未知 route 的限次 browser harvest、company_spa 识别后升级具体 adapter；BYD 只在验证路由生成稳定后缓存/离线生成。Moka、快手、JD 校招、农行、Google 没有本轮反证可推翻现有浏览器依赖。

预估收益应写成可测模型：`每轮节省 = 新迁移成功的源数 ×（旧浏览器中位耗时 − 新 HTTP 中位耗时）− 新增探测/维护耗时`。先对同一源比较实际 job ID 集合、正文、jd_url、reported_total 和完整性，再报时间正负变化；没有同源 live 对拍，不填写“省 80%”一类数字。

文档建议保留一页当前架构/产品决策与不变量入口；每条决策有日期、证据、替代/失效条件；事故详细过程进入独立文档。同步 AGENTS/CLAUDE 关键入口与权限边界。当前 711 行精简已发生，下一步重点是事实更新机制，不是继续按行数削减。

### 不建议改

- **不重写 Next/Python/PG，也不提前上 Redis、Celery、K8s、向量检索。**本轮已证问题在生命周期、证据、采集契约；新增服务不会自动修复，反而增加运行维护。
- **不把实时探活重新放到官网点击前。**保留直跳和后台/非阻塞治理；历史点击延迟教训与当前实现一致。
- **不取消硬门来填满 Today。**先区分真实供给不足、字段未知、召回遗漏和错误分类，防止数量好看但相关性变差。
- **不因列表小于数据库就扩大 absence，更不批量删除 stale active。**集合不完整与岗位关闭是两种不同事实。
- **不取消空值保留、expired sticky 或写失败不回退。**这些局部不变量正确；F1 要补的是跨删除生命周期。
- **不因为 80 用户就关闭全部长尾、海外或洞察，也不继续无条件扩量。**改为有需求缺口和治理预算的定向扩量；既防供给不足，也防数字驱动的无效投入。
- **不按 YAML 数量把调度器搬走，不按表大小立即换检索引擎。**先证明实际成本/可靠性/性能超过现有架构边界。
