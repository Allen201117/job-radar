# 洞察库重复公司画像：全集、来源与合并方案

> 2026-10-11 真库只读快照。§0~§7 是调研当时写的（那时没有改任何线上数据和代码）；创始人同日同意按建议执行，实施记录在 §8。
> 清单（136 组逐组、629 对逐对）：`docs/reviews/2026-10-11-evidence/insight-duplicate-profiles-list.md` 与同目录 `insight-duplicate-profile-pairs.csv`。
> 快照规模：公司画像 1,511 个、洞察主体 2,184 个、洞察条目 22,371 条；岗位库在招 441,217 个岗 / 1,719 个公司名。

## 0. 一页结论

| | 数字 |
|---|---:|
| 捞出来的候选对（8 路信号并集） | 629 对，涉及 543 个画像 |
| 逐对判完后还没归类的 | 0 |

三件用户看得见的事，都是重复画像直接造成的：

1. **同一家公司的说法和岗位分在两个画像上，洞察库里一张带说法的卡都出不来**：17 家（京东方 18 条说法、招商局集团 16 条、蒙牛 15 条、传音 12 条、隆基绿能和东山精密各 11 条…）。
   说法挂在一个没有岗位的画像上，岗位挂在另一个没有说法的画像上。
   136 组里这样挂在「没有主体的画像」上的在展说法共 255 条；其中有些公司出得来卡，但只出了一部分（腾讯音乐：17 条挂不出来，卡上只有另一个画像的 12 条）。
2. **同一家公司出两张及以上带说法的卡**：16 家（云南白药、华润三九、国投证券、云尖信息各 3 张；贝壳、金山办公、中核集团、三只松鼠等各 2 张）。
3. **点开岗位的洞察抽屉，打开的不是有内容的那个画像**：6 个岗位公司名、3,793 个在招岗。
   例：1,162 个「阿里巴巴」的岗，抽屉打开的是「阿里巴巴控股集团」那个画像，种子画像上的 2 条人工洞察和 2 条校招周期看不到。

还有一件看不见但在花钱的事：重复画像各自排队跑搜索 + 大模型。136 组里有 30 组、至少 37 家次是同一家公司重复跑出来的（多出 347 条说法）；
待删的 179 个画像里还有 96 个没跑过、正排在队列里等额度（全天通用搜索额度 42 次，这个数取自 CLAUDE.md 10-10 的记载，本次没重量）。

**不堵住来源，合并完当晚就会长回来**：待删的 179 个画像里，121 个的名字仍是启用中的招聘源的公司名，
每晚的「按源名补画像」只比对正名、不看别名，会按原名重建。所以顺序必须是先改代码、再合数据。

## 1. 怎么数的

两两比较全部 1,511 个画像的正名和别名，八路信号取并集，任何一路命中都进候选（一对可以同时被几路命中）：

| 信号 | 说明 | 命中对数 |
|---|---|---:|
| 线上归属门 | 直接用 `lib/insight-match.ts` 跑全部画像两两（归一后全等 / 有资格的子串） | 288 |
| 别名 = 别家正名 | 精确字符串 | 5 |
| 爬虫侧归一全等 | `bu_extract.normalize_company` | 13 |
| 同一个岗位公司名被两个画像认领 | 两个模块各自的归属口径 | 314 |
| 品牌核心词 | 去掉「校招 / 实习 / 英文尾巴 / 括号 / 公司后缀」后相等或互为前缀 | 353 |
| 英文词相同 | 名字里的英文词相等（Tongdun、Zhihu…），纯英文名整名归一相等 | 67 |
| 同一个招聘门户 | 两个画像的源或在招岗指向同一个门户租户（与名字无关） | 161 |
| 必投清单同一条目 | 清单里同一家公司的名字 / 模式命中两个画像 | 337 |

每一对的判定依据是三样东西：名字、源指向的招聘门户、在招岗链接的门户前缀；拿不准的再抽在招岗标题看。
136 组「同一家」里，93 组两边指向同一个招聘门户，29 组是必投清单里的同一条目，2 组是别名本来就登记着，
12 组只凭品牌名相同（「X 校招」对「X」、同一法人名只差括号、改名迁移里有记录的旧名），清单里逐组写了判据。

反方向也查了：拿 130 组常见外企的中英文名对照（西门子 / Siemens、星巴克 / Starbucks…）去找「两边各有一个画像却没进候选」的，0 组；
只补进来 2 对纯英文短名（DBS、JLL）。

复核了任务背景里的两个数：两个模块条数不一致的公司 4 家（字节跳动 28,632 对 20,177、大疆 678 对 140、协鑫、比亚迪），与背景一致，差值随当天岗位数小幅变化；
有在展主体的 1,352 个画像里 0 岗 100 个，一致。

### 100 个 0 岗画像的拆解

背景里的「37 家同品牌的岗挂在另一个名字下」是子串启发式的上限。逐家判完：

| 类别 | 个数 |
|---|---:|
| 重复画像，同一家的岗挂在组里另一个名字下 | 21 |
| 重复画像，整组现在都没岗 | 11 |
| 国聘「子公司（集团）」写法的画像 | 45 |
| 源改名后留下的旧名 | 1 |

## 2. 重复是怎么来的

所有建画像的入口都拿「名字完全相等」当去重键，名字写法不同就各建一个。画像的来源能从数据痕迹里分出来：

| 来源 | 全库 | 136 组的 315 个成员 | 待删的 179 个 |
|---|---:|---:|---:|
| 按招聘源的公司名建（每晚 `seed_from_sources`、加源、自动扩源） | 1,206 | 255 | 155 |
| 迁移里的种子画像（带别名） | 38 | 18 | 3 |
| `bu_extract --create-profiles` 按岗位公司名补建 | 188 | 5 | 4 |
| 按必投清单名建（校招周期链路） | 54 | 24 | 5 |
| 按源名建、该源后来改名或删除 | 8 | 7 | 6 |
| 其它（海外必投清单名等） | 17 | 6 | 6 |

所以主因不是 `bu_extract`，是**源的公司名写法**：

- 同一家公司的社招 / 校招 / 实习各一条源，公司名分别写成「X」「X 校招」「X 实习」。全库这样的源 56 条，对应 50 个岗位公司名、11,323 个在招岗；136 组里 37 组含这种成员。
- 同一家公司的两条源一条写「X」一条写「X 英文名」。全库 1,722 条源里 280 条是「中文 + 英文尾巴」写法；136 组里 88 组含这种成员。
- 必投清单用品牌短名（腾讯音乐、中通），源用另一个写法（腾讯音乐 TME、中通快递），校招周期链路按清单名又建一个。
- 种子画像用了第三种名字（苹果中国、微软中国、伊利股份、海尔智家）。
- 源改名（万达控股集团 → 万达集团、领益智造 → 特变电工）后旧名画像没人收。

`bu_extract` 补建的 188 个里 156 个是国聘「子公司（集团）」写法，属于母子关系，不是重复；它造成的重复只有 5 个。

各入口现在的状态：

| 入口 | 建画像前认不认别名 | 备注 |
|---|---|---|
| `insight_backlog.seed_from_sources`（每晚） | 不认 | 待删画像里 121 个会被它当晚重建 |
| `insight_backlog.fetch_one_company`（校招周期链路、单公司现查） | 不认 | 待删画像里 12 个是必投清单名 |
| `/api/sources` 加源、`auto_discover` 自动扩源 | 不认 | 只在新加源时触发 |
| `/api/insights/admin` 录入洞察 | 不认 | |
| `/api/insights` 抽屉现查 | 认（10-10 已改成用画像规范名） | |
| `bu_extract --create-profiles` | 认（正名 → 别名 → 归一名唯一） | |

## 3. 合并方案

### 3.1 留哪个

规则：留干净的品牌名。没有「校招 / 实习」后缀的优先；有纯中文写法的优先于「中文 + 英文尾巴」；种子画像优先；再并列看名下内容多少。
规则挑得不合适的 22 组人工指定了（跨语言的组留岗位卡上用的名字，如 Apple、Microsoft 微软；规则挑到法人全称的改留品牌名，如华润三九、爱奇艺、贝壳）。
清单里每组的「留」那一列可以逐行改，改了只影响卡片上显示哪个名字，不影响迁移行数的量级。

### 3.2 每张表怎么动

| 表 | 动作 | 行数 |
|---|---|---:|
| `company_profiles` | 删 | 179 |
| `company_profiles` | 留下的那个加别名、补它空着的事实列 | 136 个画像，新增别名 181 个 |
| `insight_subjects` | 改挂到留下的画像（公司主体 37 个同时改名，业务线 106 个） | 143 |
| `insight_subjects` | 删（留的那边已有公司主体 102 个；业务线同名 52 个） | 154 |
| `insight_items` 说法 | 改挂（在展 450、已退役留档 322） | 772 |
| `insight_items` 人工录入 | 改挂 | 2 |
| `insight_items` 官方事实 | 改挂 50；留的那边已有同项的改成退役 21 | 71 |
| `insight_items` 派生数据 | 跟着被删主体的删掉，其余改挂；当晚由 `bu_signals` 全部重算 | 2,010 |
| `insight_subject_daily`（每日快照） | 随被删的 154 个主体一起删 3,798；随改挂的主体保留 4,505 | 8,303 |
| `recruitment_cycle_observations` | 改挂 | 4 |
| `insight_disputes` / `insight_submissions` / `company_hiring_monthly` | 不涉及 | 0 |

几条必须守的规矩：

- `insight_subjects.company_id` 和 `insight_items.company_id` 都是删画像时级联删。**先改挂、后删画像**，并且放在同一个事务里；顺序反了说法就跟着没了。
- 说法条目的 `subject_id` 全库都是空（公司级），只改 `company_id` 就行。派生条目都带 `subject_id`，要跟主体一起处理，否则会撞「同一主体同一指标只许一行」的唯一约束。
- 公司主体迁过去时要同时把名字改成留下的画像的正名。不改的话，`bu_extract` 下一轮按名字找不到它，会再插一个公司主体，同一个画像下出现两个。
- 28 组里两个以上成员各有在展说法（除最多的那个成员外共 186 条）。全部改挂会让同一张卡上同一个话题出现两条。
  建议每组只保留说法最多的那个成员的在展说法，其余成员的改成退役留档：这样在展说法改挂 324 条，另有 186 条改成退役（其中 60 条原本就在留下的画像上）。等这家公司下次重跑搜索时会整体换新一代。
- 每日快照：被删的公司主体那 3,798 行里有一部分是真实历史。合并当天留下的主体在招数会跳一下（两个名字的岗加到一起）。
  要保住趋势，需要把被删主体的每日数按日加到留下的主体上。字节跳动 / 抖音、大疆 / 大疆创新这两组不能加：每日数是 `bu_signals` 按「正名 + 别名」取岗写的，
  留下的那边已经把另一边的岗算进去了，再加就是重复。不做按日相加的话，这 136 家的 30 天趋势要从合并日重新攒。
- 国聘括号变体那 15 个 0 岗残留**不登记成别名**：括号里的集团是错的，登记了等于把错的归属写进别名。

### 3.3 执行顺序

1. 先合代码，堵住来源（§2 表里四个「不认」的入口改成先按正名 + 别名查、查不到才建），加一条每日体检：「别名与别家正名 / 别名相同的画像对数」和「归一名相同的画像对数」，正常值 0。
2. 再合数据：一个迁移文件、单事务，清单冻结在文件里。事务开头按清单核对每组的现状（成员都在、行数与本报告一致的容差内），对不上就整体回滚。
3. 合并前把要删的 179 个画像及名下主体、条目、每日快照导出一份留底。删画像是不可逆的，回滚只能靠这份留底。
4. 上线当晚看 `bu_extract` / `bu_signals` 台账，次日复核：136 家各只剩一个画像、两个模块条数一致、17 家原来出不来的卡出来了、没有画像被重建。

迁移文件和代码都还没写，等清单确认后再动。动之前按清单 136 组逐组再核一遍现状。

### 3.4 对线上归属门的影响

`lib/insight-match.ts` 的规则不用改。合并后的变化：

- 「归一后全等」的画像对现在有 16 对，抽屉在这种情况下取 id 排在前面的那个，等于随机。合并后这 16 对里 12 对消失（同一家的），抽屉与洞察库的归属就对上了；
  剩下 4 对是阿里巴巴 / 蚂蚁集团（去掉别名「蚂蚁」即解）和三对拿不准的（三一、海尔、爱慕）。
- 剩下的是归属门自己的洞，不是重复画像问题，见 §5.4。

## 4. 「别名 = 别家正名」怎么定

精确相等的 5 对，加上归一后撞上的 3 对：

| 画像（别名） | 撞上的画像 | 建议 | 依据 |
|---|---|---|---|
| 字节跳动（抖音、Douyin） | 抖音 | 合并，留字节跳动 | 「抖音」这条源是 `bytedance.jobs.feishu.cn`，字节自己的飞书门户，9 月 26 日才接；它的 7,265 个不同标题里 6,884 个（94.8%）在字节跳动名下也有 |
| 大疆（大疆创新） | 大疆创新 | 合并，留大疆 | 同一家的两个门户（140 岗 + 538 岗），标题只重 1 个，是互补不是重复 |
| 京东（京东集团） | 京东集团 | 合并，留京东 | 京东集团是源改名前的旧名，0 岗，名下 20 条在展说法 |
| 苹果中国（Apple） | Apple | 合并，留 Apple | 种子画像 0 岗，4,780 个岗在 Apple 名下 |
| 海尔智家（海尔） | 海尔 | 不合并，从海尔智家的别名里去掉「海尔」 | 海尔智家是上市主体；「海尔」那个画像有自己的源和 1,089 个岗；属于 §0 里「拿不准」那 9 对 |
| 阿里巴巴（蚂蚁） | 蚂蚁集团 | 不合并，去掉别名「蚂蚁」 | 蚂蚁集团是关联公司，有自己的画像和门户 |
| 深度求索（幻方） | 幻方量化 | 不合并，去掉别名「幻方」 | 两家公司 |
| 三一重工（三一） | 三一集团 | 等创始人定 | 上市主体对集团，同一个门户；「三一」两个字归谁要定 |

两个模块的口径建议统一成一个：`bu_signals` 不再自己用「正名 + 别名」去岗位库取岗，改用 `bu_extract` 那套归属（每个岗位公司名只归一个画像）。
这样即使以后别名又撞了，也只会算给一个画像，不会两边各算一遍；协鑫、比亚迪那种归一名兜底的差异也一起消失。
线上抽屉是第三套口径（归一全等时取 id 靠前的），合并后在这 136 组上不再有分歧，可以不动。

## 5. 顺带发现（不在本任务范围，都没动）

### 5.1 「东鹏饮料」这条源抓的是东鹏控股（瓷砖卫浴）

门户 `dongpeng.zhiye.com` 的页面标题是「广东东鹏控股股份有限公司」，在招岗标题是「产品企划（卫浴）」「机电技术员（广东清远）」。
源名却是「东鹏饮料」（行业标成食品饮料），100 个在招岗挂错名。原来叫「东鹏」的那条源在迁移 186 里被当成重复停掉了。
「东鹏饮料」画像名下还有 1 条官方事实和 2 条年报数据，和这些岗不是一家公司。

### 5.2 「上海鹰瞳医疗科技集团股份有限公司」这条源抓的是祖龙娱乐

moka 租户 `zulong` 的社招门户，在招岗标题是「剧情导演」「数值策划（女性向）」「系统策划（以闪亮之名）」，27 个岗挂在鹰瞳医疗名下。同一个租户的校招源名字是对的（祖龙娱乐）。
这一条只看了岗位标题，没打开门户核自报公司名。

### 5.3 「抖音」这条飞书源和字节官网的岗大面积重合

见 §4。按标题算，抖音名下 8,455 个在招岗里 8,034 个在字节跳动名下有同标题的岗。两个门户链接不同，岗位库的链接去重拦不住。
这是按标题比的，没有逐岗对岗位编号；如果确实是同一批岗，等于约 8,000 个岗在库里各存了两份。这条源留不留，和画像合并是两个决定。

### 5.4 归属门把不同公司放行

`lib/insight-match.ts` 现在认为下面这些是同一家：大华集团 / 大华股份（「股份」「集团」都算装饰词）、沃尔沃 Volvo Cars / Volvo Group、
中国电信 / 中国电信国际、中国铁建 / 中国铁建国际集团、京东 / 京东科技（「国际」「科技」「投资」算装饰词）。
目前没出事是因为这些名字各有自己的画像，精确匹配优先；哪天其中一个画像没了，岗就会归到另一家头上。

### 5.5 必投清单的模式串到别家

「吉利德 Gilead」用项目自己的 `must_apply.resolve_owner` 跑，归到了必投的「吉利」（实跑复现）。
清单里宁德时代的模式是 `%宁德%`、ABB 是 `%ABB%`，按模式的写法会分别命中宁德新能源（ATL，另一家公司）和 AbbVie / 雅培 Abbott；这两条是照模式推的，没有跑看板的统计去验。

### 5.6 国聘子公司画像把集团的说法挡在抽屉外

`bu_extract` 给 156 个国聘「子公司（集团）」名字各建了画像。在这之前，这些子公司的岗点开抽屉会落到集团画像（中国能建、南方电网…名下各有 9~22 条说法）；

### 8.2 改了什么

- **堵来源**：建画像一律先按「正名 → 别名 → 归一名唯一」找，找不到才建。爬虫侧 `crawler/company_profile_resolve.py`
  （按源名补画像、单公司取画像、自动扩源三处改走它），网站侧 `lib/insight-profile-store.ts`（加源、后台录入洞察、抽屉现查的占位，共四处改走它）。
  归属规则不另写一份，两端都用 `bu_extract` 给岗位认画像的那一套，共用夹具 `tests/fixtures/profile-resolve-cases.json`。
- **招聘渠道后缀进了归属规则**：名字末尾的「 校招」「 实习」「 社招」不算公司名（`bu_extract.profile_name_key`）。
  只登记别名兜不住新公司——以后新接的公司，源照旧叫「X」「X 校招」，还是会各建一个画像。
  「中文 + 英文尾巴」没有进自动规则：沃尔沃汽车和沃尔沃集团在库里就是「沃尔沃 Volvo Cars」「沃尔沃 Volvo Group」，自动并会并错；这一类交给体检点名、由人判。
  用最新快照核过：现在没有任何在招的岗位公司名要靠这条规则才认得到画像，它只管以后新来的名字。
- **两个模块口径统一**：`bu_signals` 取岗改用 `bu_extract` 的归属（`fetch_owned_job_companies`），每个岗位公司名只归一个画像。
- **受合并牵连的两处下游**（代码审查查出来的）：校招周期链路判「这家已有时间线」原先拿清单名比画像正名，合并后清单写「中通」、画像叫「中通快递」
  就永远判不出已覆盖，会每轮重复花搜索额度——改成按归属判；搜索富化排队时的在招数原先只按正名数，岗位挂在别名下的画像会排到队尾——改成正名加别名一起数。
- **两条每日体检**（`crawler/audit_contract.yaml`）：「几对画像用了同一个名字」正常值 0，合并前真库实测 6；
  「几对画像只差后缀或英文尾巴」正常上限 1（沃尔沃那一对），合并前实测 173。
- **数据迁移** `supabase/migrations/317_merge_duplicate_company_profiles.sql`：单事务，画像清单冻结在文件里，开头断言现状、结尾断言结果，
  任何一步不过整体回滚；主体的去留在库里现算（`bu_extract` 每晚增删业务线主体，冻结主体 id 过一晚就对不上）。
  动之前把涉及的行整份留底到库里的 `archive` 模式（`archive.merge_20261011_*` 七张表，不对外暴露）；合并前的快照另存了一份在本机备份目录。
