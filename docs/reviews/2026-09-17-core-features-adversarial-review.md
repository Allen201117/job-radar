## 2. 推荐链：第一性原理下的判断

现行是标准的两阶段（SQL 召回 → JS 硬门 + 加权打分 → 分区 + 配额），与 LinkedIn L1/L2、ZipRecruiter 多阶段专利的形态一致；
调研（researcher，来源见文末）确认在「无行为数据 + 显式偏好」的约束下，**先结构化硬门、再关键词、最后多样性**就是业内做法，
没有必要上向量库。真正的差距在三处，本轮改了前两处：

1. **召回窗口不按「该留谁」截断**（已修）。方向 tsquery 命中集 ≫ 份额时，窗口按城市→最新排，精确标题命中被砍。
   加「用户原词在标题里」作第二排序键（城市之后）。
2. **词库是互联网口径，非互联网画像召回为零**（已修）。`job_function` 是标题+正文分类好的物化列，加第四层
   `job_function = any(目标职能) AND search_doc @@ 城市`（BitmapAnd 两个索引，182~398ms）。三种反例都实测过并否掉
   （见 CLAUDE.md「/today 召回加了第四层」）。
3. **/today 与 /jobs 是两套打分**（未改，出 spec）：`lib/opportunities/scoring.ts`（方向 40/30/22、城市 15、阶段 10、行业 10、
   技能 ≤15、新鲜度线性）与 `lib/scoring.ts`（方向 30/15、城市 20、公司 15、关键词 5/2.5、新鲜度 10 二值），硬门也不同
   （/today 有阶段/学历/行业硬门，/jobs 没有）。同一个用户在两页看到两种排名。统一成一份 MatchFacts + 一份权重表是
   正确方向，但要用 match-eval 在两个页面同时验收，属单独立项。

对拍数字（scratchpad w2-measure，真实 stage-1 SQL + 真实 stage-2 引擎，18 个画像，可展示岗数 改前 → 改后）：

## 13. 搜索「等了超过 3 秒」33.75%：第四、五层病根（2026-09-23）

起点：结构性审计 `exp.search_slow_rate_7d` 连续 5 天 35%~42%（阈值 ≤20%），当天 33.75%。

**先量**：近 7 天 `events.search_result` 全集 80 次 / 8 个用户，逐条拉出条件 + 画像 + 页面来源（不抽样）。慢的 27 次：
/campus 全部校招岗 10 次（其中 1 次 ≥10s）、/jobs 不加筛选 6 次、只选实习 / 实习+销售 2 次、空偏好用户「北京」系列 4 次、
09-16 旧代码（09-18 粗排上线前）2 次；其余 3 次（青岛 ×2、IC 关键词 ×1）库上本来就快（36~82ms），慢在函数冷启动 / 当时库忙，代码层没有可修的。
复现：用生产同一份 `lib/jobs-store/search.ts` 拼 SQL（jobsQuery 换成 psql），每条都拿当时那个用户的真实偏好与操作记录跑 `EXPLAIN (ANALYZE, BUFFERS)`。

**第四层：规划器估错行数。** `coalesce(job_scope,'domestic')='domestic'` 是表达式、无统计 → 估 0.5%（实际 67%）→
「取最新 1000 行」被规划成 Parallel Seq Scan + top-N 排序（13.9 万 buffer，7.9 万从盘读）。
改写成逐值等价的 `(job_scope='domestic' or job_scope is null)` → Index Scan（1.5k buffer）。
⚠️ 这也更正 §11 追记三「SQL 已不是瓶颈」：那次只测了带方向词的登录态，不加筛选 / 只选校招 / 只选实习这三类当时同样在整表扫。

**第五层：招聘类型没索引。** 库机 2GB 内存 / 2.26GB 数据，冷缓存每回表一行 0.1~0.3ms；实习只占 active 6%，
按时间翻要回表 2.9 万行（同一条查询热 76ms、冷 2.1~4.6s）。新增 `idx_jobs_active_recruitment_first_seen`（5.5MB）+
两处 SQL 形状（规划器不会自己把 OR 分配进去）：无粗排时预筛拆两支 `union all`；粗排收窄按类型拆三支。

**顺带两处**：① 选了招聘类型时 `exactTotalWhenCapped` 先 `exists` 查未分类行（有就弃权）——此前全表 count 0.6~2.4s 算完被门④丢掉；
② 有偏好记录但没有任何粗排信号（全库 13/68 个偏好行）的用户按匹配度排时，FTS 路径与匿名同用 1000 窗（原 8000 行 5.7MB）。

### §13 追记：计数缓存为什么对校招 / 城市不命中（2026-09-23 晚，main 86439f42）

**根因（线上 A/B 实锤）**：`unstable_cache` 在动态请求里把「路径 + **解码后**的查询串」拼进缓存条目名，Vercel 数据缓存把它放进 HTTP 请求头；
请求头只能是 Latin-1，含中文时读、写都在发出前抛错，被 Next 吞成一行 warn → 永远不命中、每次回源、不报错。
同一条计数（「不加筛选」，缓存里本来就有）只在网址后多挂一个无关的 `&zz=中`：尾段 6~52ms → **678~1,738ms**，返回的数字也变成现算的新值。
Next 官方缺陷 [vercel/next.js#76286](https://github.com/vercel/next.js/issues/76286)，修复 PR #96937 只进了 16.x（下载 16.3.6 核过有），15.5 线到 15.5.26 都没 backport。
同一天洞察库那条线独立查到同一个根因（`lib/cache-outside-request.ts`），并发现第二个坑：接口路由会等过期条目的后台重建跑完才结束响应。

**修法**：`lib/request-safe-cache.requestSafeCache` = `unstable_cache` + 每次调用自动经 `callOutsideRequestScope`（两条线共用一套机制），
全站 15 处缓存统一换用，契约测试禁止直接调 `unstable_cache`；回归测试在本机复现缺陷（原生两次回源、包装后第二次命中、缓存键不变）。
另把用户隐藏岗拆出计数的缓存键：总数 = 共享计数 − 隐藏岗落在条件内的条数（主键取，0.4~0.6ms），逐值相等；
省目标的按地点复核（主干同日加的）对两部分各做一遍再相减，补了组合用例（外省的隐藏岗不能多减）。
