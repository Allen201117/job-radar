# 库的预读并发（effective_io_concurrency）：实测与落地（2026-10-12）

## 结论

香港 jobs 库的 `effective_io_concurrency` 是默认值 1。它只管一种读法：先从索引拿到一批行的位置、再回表把这些块读出来（位图堆扫描）。
对这种查询，数据不在缓存里时每读一块从 0.149ms 降到 0.033ms（取 64），语句整体快 2~3 倍；别的读法吃不到。

落地：应用连接池的每条连接在建立时带上 64（`lib/jobs-store/client.ts`）。库级 / 角色级配置没动，爬虫不受影响。

## 背景

此前「热几十毫秒、冷几秒」的结论是「加索引 / 瘦身救不了，只剩加内存」（见 CLAUDE.md /today 召回一节）。那次量的是要读多少块，
没人量过每块读多快。2026-10-12 凌晨洞察抽屉那条「按公司取全部在招行」的查询冷读 8.6 秒，才查到这个参数是默认值。

## 怎么量的

- **输入**：51 个画像就绪用户的 /today 召回 SQL（现跑、限定重算、读快照三条）；近 30 天 378 次真实搜索去重后 120 种里的 56 种；
  36 个城市（18 个只选城市、18 个城市 + 校招）；4 种匿名默认态。SQL 由生产代码原样生成（加载 `search.ts` / `opportunities.ts`，
  只把取数入口换成「先 EXPLAIN 再真取行」）。
- **设计**：四轮，每个输入每轮只跑一种设置，四轮下来 1 / 16 / 64 / 200 各跑一次（拉丁方）；每轮执行顺序重新打乱。
  四种设置读的块数合计 81.5 万 / 83.2 万 / 80.7 万 / 82.0 万，基本持平。
- **每条语句**：`EXPLAIN (ANALYZE, BUFFERS)` 冷跑一次，紧跟着同设置再跑一次当「数据在缓存里」的基线。数字都是库内执行时间。
- **时段**：

  | 轮 | 北京时间 | 当时库上的情况 |
  |---|---|---|
  | R1 | 08:24~08:37 | 校招爬虫在写，每秒写 253 行 |
  | R3 | 08:44~09:17 | 基本无写入（每秒 12 行），但撞上每日体检的全表扫 |
  | R2 | 09:24~09:38 | 巡检写库，33 个其它连接，每秒写 150 行 |
  | R4 | 09:38~10:07 | 34 个其它连接，每秒写 191 行（峰值 404）；三条测量语句同时跑；快照后台刷新也在跑 |

  另有一轮空闲时段（08:40，无写入）拿 24 个前面没读过的城市补测。
- **并发影响**：测量时另开一个只读会话，每 0.1 秒随机读 jobs 堆上的一个块（库内掐表）并看一眼谁在跑、在等什么。
  测量语句开头带标记，所以每个样本都对得上「当时测量会话在跑哪条、预读设多少」。三轮共 3.5 万个样本。

## 数字

### 按查询类型（冷跑，中位 / 九成内 / 最大 / 合计）

| 查询 | 条数 | 预读 1 | 16 | 64 | 200 |
|---|---|---|---|---|---|
| /today 现跑召回 | 51 | 0.76s / 4.10s / 6.51s / 82.6s | 0.45 / 1.78 / 3.57 / 39.2 | 0.26 / 1.29 / 2.18 / 27.1 | 0.23 / 1.25 / 2.35 / 26.6 |
| /jobs 登录搜索取候选（走位图的） | 38~40 | 0.39s / 3.55s / 5.55s / 34.4s | 0.16 / 0.82 / 2.67 / 13.5 | 0.17 / 0.73 / 2.60 / 11.4 | 0.17 / 0.62 / 2.50 / 11.9 |
| 只选城市 | 16 | 0.34s / 2.70s / 2.75s / 9.8s | 0.08 / 0.65 / 1.10 / 3.3 | 0.05 / 0.53 / 1.02 / 2.2 | 0.04 / 0.35 / 0.48 / 1.8 |
| 城市 + 校招 | 16~17 | 0.16s / 0.32s / 1.57s / 3.8s | 0.05 / 0.19 / 0.20 / 1.4 | 0.04 / 0.26 / 0.33 / 1.4 | 0.04 / 0.12 / 0.13 / 0.8 |
| 全部带位图堆扫描的语句 | 206~208 | 0.18s / 2.75s / 10.7s / 165.0s | 0.11 / 1.03 / 3.57 / 66.1 | 0.07 / 0.73 / 2.60 / 50.6 | 0.08 / 0.74 / 2.50 / 49.2 |

每读一个不在共享缓存里的块（冷跑减热跑，再除以读块数）：1 → 0.149ms，16 → 0.046，64 → 0.033，200 → 0.028。
空闲时段那 24 个没读过的城市：0.066 / 0.024 / 0.014 / 0.016ms。

这里的「冷」是当时的自然状态：读块里混着系统缓存命中，所以预读 1 的平均值被稀释了；真从盘上读是 0.2~0.45ms（看索引扫描那几类的每块耗时）。

### 吃不到的

| 查询 | 走的是 | 实测 |
|---|---|---|
| /today 读快照（线上请求实际先跑的那条） | 按主键逐行的索引扫描 | 冷跑 102 次：中位 0.16s、九成内 0.42s、最大 0.74s；四种设置合计 5.1 / 5.7 / 5.6 / 4.1s，没有趋势 |
| /today 限定重算（先冷跑它） | 位图，但一半读块是主键叶子页 | 合计 5.7 → 3.8 / 4.2 / 4.3s，只有取堆块那一半变快 |
| /today 限定重算（线上顺序：读快照之后） | 同上，此时已读热 | 中位 50~67ms，四种设置没差别 |
| 走索引扫描的搜索候选（13 / 56 种）、匿名默认态 | 按时间索引顺扫 | 每块 0.18 / 0.17 / 0.22 / 0.12ms，没有趋势 |
| 「北京」只选城市 | 按时间索引顺扫 | 0.72 / 0.16 / 2.13 / 0.72s，只跟当时缓存有关 |
| 「不加筛选」的真实总数计数 | 全表顺扫 | 2.2s，冷热一样 |
| 位图扫描里读**索引**页（GIN 页、主键叶子页） | 不预读 | 索引页冷的语句每块仍是 0.2~0.35ms |

### 反方向

- 同一输入预读 1 对 64 共 119 对（带位图）：96 对明显更快，7 对明显更慢，其余差不多。7 对逐条看过：
  6 对是 64 那一轮要读的冷块多出几成到几百倍（例：46 块对 2,467 块、5 块对 1,293 块），其中 3 对冷的主要是索引页；
  1 对读块相同、热跑本身就慢了 5 倍（当时有别的负载）。没有因为调大而变慢的查询形状。
  另外「北京」只选城市（索引扫描，不在这 119 对里）也是 64 那一轮更慢，与这个参数无关。
- 数据都在缓存里时（同一输入跨轮配对的热跑）：耗时比值中位 0.99~1.03，没有额外开销。
- 规划器不看这个参数：171 条真实 SQL 按 1 / 200 / 1 / 200 各 EXPLAIN 一次，计划形状随设置变的 0 条
  （3 条在同一设置下两次就不一样，是 GIN 的代价估算读实时统计造成的）；只走 btree 的对照语句代价估算逐位相同。

### 对别的会话的影响

旁路会话随机读一个堆块的耗时，按「当时测量会话在跑什么」分组（三轮合并）：

| 当时 | 样本 | 中位 / 九成 / 最慢 1% | 超过 1ms | 超过 5ms |
|---|---|---|---|---|
| 没有测量语句在跑 | 30,505 | 0.04 / 0.56 / 1.10ms | 1.3% | 0.1% |
| 冷跑，预读 1 | 1,445 | 0.04 / 0.54 / 1.17 | 1.8% | 0.0% |
| 冷跑，预读 16 | 548 | 0.04 / 0.67 / 2.53 | 6.2% | 0.2% |
| 冷跑，预读 64 | 578 | 0.04 / 0.57 / 2.10 | 2.9% | 0.2% |
| 冷跑，预读 200 | 564 | 0.04 / 0.66 / 2.74 | 6.4% | 0.2% |

- 别的会话里「在等磁盘读」的平均个数：0.19（基线）对 0.18~0.30；「在等写日志」基本是 0，各组都一样。
- 16 / 64 / 200 之间没有单调关系（64 反而最低），差别在噪声里。测量语句热跑时尾部也会变厚（3.8%~7.2%），
  说明一部分是两核机器上的计算争用，不全是预读。
- R4（爬虫重度写库 + 三条冷查询同时跑）里 64 的每块耗时 0.039ms，单条跑的几轮是 0.022~0.042ms。

## 三种落法

| | 改哪里 | 影响面 | 没量到的 |
|---|---|---|---|
| ① 个别查询包事务级设置 | 搜索取候选、计数、召回共 3~4 处 | 只这几条；每条多 3 次往返 | 函数到库的往返耗时 |
| ② 连接池启动参数 | `lib/jobs-store/client.ts` 一处 | 应用全部查询 + 用这个池的脚本（快照后台刷新等）；不含爬虫 | 很多用户同时冷查询的叠加 |
| ③ 角色 / 库级配置 | 库上一条 `alter role` | 所有连接，含爬虫和夜间任务 | 爬虫侧完全没量 |

选了 ②，取 64（创始人 2026-10-12 拍板）：比 16 现跑召回合计再少 31%、搜索取候选再少 16%；200 没有更多收益；并发数据里 64 不比 16 差。
③ 没做：爬虫写库前按链接批量查旧行（500 条一批）、按源取在招岗、按公司取岗都是位图堆扫描，改了会跟着预读，
几十条爬虫连接同时预读的叠加没量过。

## 落地

- `lib/jobs-store/client.ts`：连接池 `options: "-c effective_io_concurrency=64"`（`JOBS_IO_CONCURRENCY`）。
  已在真库上核过：带这个启动参数的连接读到 64，同时建的另一条不带的连接仍是 1；事务里 `set local` 照样能盖过它。
- 环境变量 `JOBS_DB_IO_CONCURRENCY`：`off` 关掉，1~1000 的整数改值，其它写法按默认值并告警。
- 洞察抽屉那条查询自己的事务级 64 留着（它不跟着环境变量变）。
- 回归：`tests/jobs-store-io-concurrency.test.js`。

## 没量到的 / 局限

- 「冷」是自然状态，不是强制清缓存后的状态；同一份数据只能冷一次，所以靠拉丁方轮换 + 配对，而不是同一时刻的 A/B。
- 数字是库内时间，不含函数侧计算和结果传输。/jobs 慢搜索比例（体检 `exp.search_slow_rate_7d`）能降多少，从这里推不出来。
- 真实搜索是 120 种里抽的 56 种；埋点不记排序方式和学历等筛选项，一律按默认「匹配度」还原。
- 爬虫的写入延迟没有直接量，只看到「在等写日志」的会话数没有变多。
- 三条测量语句真正同时在跑的瞬间很少（旁路样本只有几十个），R4 的结论主要来自每块耗时没有恶化。
- 测量期间 09:43 那轮快照后台刷新和 R4 撞上了，它那轮的耗时（中位 1.86s、九成内 8.5s）不能当基线。
