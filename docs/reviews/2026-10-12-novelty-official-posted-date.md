# 判「新岗」认官方发布日：量到的数、规则、对拍（2026-10-12）

状态：代码在分支 `claude/eager-pike-f842d4`，**没推 main、没动库**。规则与 7 这个数创始人已确认（同日）。
库里的数是 2026-10-12 北京时间 20:03~20:45 在香港库上只读量的，全部是全量扫描，不是抽样；重放用的画像与召回行取自同日 22:50 之后。

## 1. 问题

读侧判「新」的地方全认首见时间（`first_seen_at` = 我们第一次抓到它的时刻），一处都不看官方发布日（`posted_at`）。
每接一条新源、每修一次翻页，对方门户上挂了很久的老岗会整批以「新岗」身份进来。

## 2. 规则

**有官方发布日、且比首见早 7 天以上的岗不算新岗**——进来那天它就已经不在「近 7 天」里了。其余一律照旧：

- 没有发布日 → 照旧按首见算。
- 发布日比首见晚 → 照旧按首见算。**只往外排、不往里加**：发布日再新，也不会把老行重新算成新岗。

实现只有一份：`lib/job-novelty.ts`（JS 判据与 SQL 判据写在同一个文件、共用同一个天数）。读侧 8 处都走它：

| 用户看到的 | 位置 | 窗口 |
|---|---|---|
| 岗位库按匹配度排：「近 7 天新增」+10 分与这条理由 | `lib/scoring.ts` | 首见 ≤7 天 |
| 岗位库登录态粗排的 +10、候选窗口的「方向 or 近 7 天」 | `lib/jobs-store/search.ts`（`prescoreOrderBy`，两处用同一个条件） | 首见 ≤7 天 |
| 卡片「新发现」徽标 | `components/JobCard.tsx` | 首见 ≤3 天 |
| 「仅新岗位」筛选 | `lib/job-filter.ts` | 首见 ≤3 天 |
| 今日推荐：「今天首次发现」理由、新鲜度分（最多 10 分，7 天衰减完） | `lib/opportunities/eligibility.ts`（`noveltyHours`，老岗为 null） | 首见 |
| 今日推荐召回的「目标城市近 7 天新岗」层 | `lib/jobs-store/opportunities.ts`（香港库路径 + Supabase 兜底路径） | 首见 ≤7 天 |
| 今日推荐「上次访问以来新增」标记（界面目前没用到） | `lib/opportunities/grouping.ts` | 首见晚于上次访问 |

`tests/job-novelty.test.js` 钉着：规则本身（含「发布日比首见晚不算新」）、JS 与 SQL 同一个天数、上表每一处都引用这一份、
`lib/` `app/` `components/` 里不许再出现手写的「现在减首见时间」。这份测试放回改前的代码上会红。

## 3. 量到的数

在招 430,312 行，带发布日的 177,740 行（41%）。

| 窗口 | 首见在窗口内 | 带发布日 | 其中发布日比首见早 7 天以上 |
|---|---:|---:|---:|
| 近 7 天 | 26,793 | 8,374 | 2,257 |
| 近 3 天 | 11,850 | 3,547 | 1,326 |
| 近 24 小时 | 6,155 | 1,311 | 781 |

（同日 08:40 另一个会话量到的近 7 天那一格是 1,564；白天又进来一批，其中字节官网当天改取法一次进来 506 行。）

### 3.1 为什么是 7

近 7 天首见、带发布日的 8,374 行，按「首见 − 发布日」分：

| 发布日更晚 | 0~2 天 | 3~7 天 | 8~30 天 | 31~365 天 | 1 年以上 |
|---:|---:|---:|---:|---:|---:|
| 248 | 5,782 | 87 | 500 | 1,446 | 311 |

两头分布，中间几乎是空的。门槛取 3 / 7 / 14 / 30 天，排除的行数是 2,344 / 2,257 / 2,109 / 1,757——3 到 7 之间只差 87 行。
取 7 是因为与「近 7 天」同一个数，说得清：进来那天就已经不在近 7 天里。

### 3.2 发布日比首见晚的有多少，各来源的发布日是不是一回事

带发布日的 177,740 行里，发布日比首见晚的 26,830 行（晚 2 天以上 25,392、晚 30 天以上 15,724）。
首见早于 7 天前、发布日却在近 7 天内的 5,639 行——如果「发布日新就算新」，这批老岗会被重新算成新岗，所以规则不往里加。

各来源写进 `posted_at` 的东西不一样（看 adapter 取的字段 + 库里的表现；后一列 = 首见早于 30 天前、带发布日的行里，发布日比首见晚 2 天以上的占比）：

| 来源 | 取的字段 | 发布日晚于首见 |
|---|---|---:|
| Greenhouse | `updated_at`（最近更新） | 3,805 / 4,261 |
| 小红书 | 发布类字段（表现为最近更新） | 1,675 / 2,263 |
| 腾讯 | `LastUpdateTime`（最近更新） | 1,290 / 2,054 |
| 蚂蚁 | 发布类字段（表现为最近更新） | 732 / 1,297 |
| 网易 | `updateTime`（最近更新） | 2,152 / 3,962 |
| 快手 | 发布类字段（表现为最近更新） | 1,333 / 2,786 |
| hotjob / wt | `publishDate` | 1,998 / 28,838 |
| Amazon | `posted_date` | 0 / 7,696 |
| 飞书系（含字节官网） | `publish_time` | 0 / 29,581 |
| SmartRecruiters | `releasedDate` | 0 / 9,827 |
| 小米（飞书私有部署） | `publish_time` | 0 / 2,923 |
| Workday / 北森多数门户 / Oracle / 微软 / 美团 / Moka（main 上） | 不给发布日 | — |

两种含义对这条规则是同一个方向：发布日很旧 = 至少这么久没人动过它，是老岗；发布日很新不等于新开的岗。
**后果**：存「最近更新」的来源，老岗只要对方近期动过就查不出来——Greenhouse 近 7 天进来 664 行，一行都不会被排除。

### 3.3 这条规则管不到的

近 7 天首见的 26,793 行里 18,419 行没有发布日，照旧算新岗：Workday 10,124、Moka 4,608、北森 1,370、Oracle 385、比亚迪 386、微软 286、DSV 215、美团 159。
Moka 的发布日期写进 `posted_at` 的改动在分支 `claude/hungry-neumann-8e59e3`，还没进 main；它上线后这条规则会多管几千行。

### 4.2 本该算新却被排除的

按规则自己的定义，被排除的每一行官网写的发布日都在首见 7 天以前，所以「官网说它是新岗、我们却不算」的情况是 0。
真正可能冤枉的是两种，都落在「老源零星进来」那 344 行里（上限，占被排除行的 15%）：

- 公司把旧岗重新挂出来，官网沿用了原来的发布日。对用户来说它确实是新开放的；我们和「之前漏抓、现在才抓到」分不开。
- 部分来源的发布日取的可能是「岗位在对方系统里的创建时间」而不是「对外发布时间」（`pick_publish_date` 的候选字段里有 `create_time`）。没有逐家核。

## 6. 重放对拍

三把尺子用的是同一个取数办法：改前的代码（`git archive` 出来的改前提交）和改后的代码各自生成 SQL，
**在同一个只读快照事务里**取回两条 SQL 各自的行编号与顺序，再让两份代码各拿自己的行重放**生产代码本身**；
「现在几点」钉死，每份代码重放两遍。两边的差异只可能来自代码。
跨境链路当晚只有 10~40 KB/s，岗位内容按岗位去重、每个只取一次，两边共用同一份内容
（头几位用户另把改后结果完整取了一遍核对：行数、顺序、层内名次逐行相同，只有「最近见到时间」因为内容来自更早的快照而有几十行不同）。

### 6.3 方向准确率（match-eval，24 格）

`scripts/match-eval` 的 6 份简历画像 + 6 份跨行业画像，各分 A（只给目标岗位 + 城市）/ B（简历画像）两种输入。

裁判 temperature 0、两边共用判决缓存，改前那份重判一遍 0 次新调用。

| | 改前 | 改后 |
|---|---:|---:|
| 严格（同一具体角色） | 407 / 448 = 90.8% | 405 / 449 = 90.2% |
| 宽松（同大方向） | 444 / 448 = 99.1% | 444 / 449 = 98.9% |

| 下降的格子 | 严格 | 宽松 | 怎么回事 |

## 7. 召回快照

快照的形状指纹是召回 SQL 全文 + 参数的哈希（`recallSnapshotKey`）。两份代码各算一遍：52 个就绪画像里 46 个指纹变了
（正是带城市新岗层的那 46 个），6 个不变（没填城市，SQL 逐字节相同）。指纹对不上 → 旧快照不用、退回现跑、现跑结果回写成新快照。
上线后这 46 位第一次打开今日推荐走的是现跑（慢的那条路），之后恢复；上线后应手动触发一次 `today-recall-snapshot` 预热，别等 6 小时一轮的定时。

## 8. 没验证的、已知的口子

- **线上没验**：没推 main；今日推荐 / 岗位库都要登录，匿名接口没有偏好、拿不到新岗分，看不出差别。
- **没填任何偏好的登录用户**：他们按匹配度排时走「按最新逐批取、攒够一页就停」的路径，老岗只在已取回的批次里沉底。
  第一页正确（见 6.2）；翻过一整批（1,000 行）之后，前一批沉底的老岗会被后一批的新岗挤到更后面，已经翻过的位置上会漏看几行。接受，注释里写了。
- **对方刷新发布日**：一条老岗进来时被判老岗，对方随后把发布日刷到首见之后，它在首见后的 7 天内会重新算新。上限就是那 7 天。
